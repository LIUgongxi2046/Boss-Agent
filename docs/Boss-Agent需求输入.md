产品需要让使用者随时交办、持续查询进展，并在本人需要处理时提供足够的信息。管理后台负责配置、模拟、检查与维护这些行为。

桌面应用通过鼠标、键盘和获准麦克风完成全部老板任务。老板和技术维护分别认证，切换入口不增加权限。窗口关闭与完整退出分别表达；完整退出默认停止本地调度，休眠恢复、重启或网络恢复后读取正式状态，核查过期授权、已取消计划及重复事件，再处理仍有效事项。未确认结果不得直接重新发送。系统通知仅展示必要摘要，私人正文不进入系统通知；通知权限关闭时保留应用内通知，麦克风权限拒绝时明确说明并保留文字输入。桌面宿主只开放经过授权的能力，不向模型开放任意本地文件、命令或凭据访问。

桌面设计检查覆盖 1024×768、1280×800、1440×1024 的内容窗口及 200% 缩放，数值为设计推断，实际兼容须验证。保留全部功能的线框、高保真页面与适用状态及素材交付。现有 API 继续按 D04/D07/D10 接入；离线时明确服务不可用。安装、启动、关闭、退出、恢复、卸载后的用户资料处理及系统权限均纳入 T02/T25 检查，卸载不得默认删除业务资料。开源调查中的其他产品平台信息保留其研究属性，不扩展本项目平台范围。

演示中的数据分为三种来源：

- `SIMULATED`：组织、人员、日程、订单、库存、财务明细、会议、审批、消息及业务事件等合成内容。
- `PUBLIC_SOURCE`：海大年报、公开报道和已核查官方资料，保留原文来源与日期。
- `RUNTIME_RECORD`：程序实际产生的模型调用、工具调用、配置操作、状态变化、耗时和用量记录。

模拟业务数据可以作为 Agent 的工作材料。模型推理、工具执行、保存、检索和页面交互需要实际运行。预设剧本描述业务事件与预期检查内容，最终回答由模型根据当次数据生成。

### 1.1 本文件采用的角色与建设范围

以下为根据用户方向形成的建设建议及演示设定。个人习惯、关注阈值、组织授权和演示时间均属于可调整的合成配置，不代表薛华本人或海大的内部制度。

| 范围 | 本次需求输入采用的定义 |
|---|---|
| 服务主体 | 一个具有明确目标、决策权限和个人记忆的老板角色 |
| 外部联系人 | 秘书、业务负责人、财务及专业人员作为资料作者、消息对象和事项负责人存在，其材料与反馈由模拟接口提供 |
| Agent 与业务使用者 | 一个老板 Agent 服务一位老板；当前建设范围不包含其他职能部门 Agent、部门工作台、部门业务账号和部门内部任务流程 |
| 老板入口 | 同一应用中的今日、聊天、经营关注、会议资料、任务与设置 |
| 管理入口 | 技术维护者配置老板 Agent、管理模拟环境和检查运行；维护身份与老板身份分别授权 |
| 业务系统 | 销售、财务、采购、生产、审批、日历与消息由关联的模拟接口承载 |
| 开源复用 | 采用一个经验证的运行项目，记录复用、扩展和自行建设的具体职责 |
| 完成范围 | 第 13 节定义的连续任务与专题分支均有可执行结果；研究资料中的产品能力不自动转为本项目交付承诺 |

需求输入记录老板目的、工作材料、行动范围和结果检查。部门业务过程用于解释资料关系及来源，专业结论由模拟接口提供。页面数量、数据库结构、最终接口路径和详细技术设计由建设任务确定。

| 水产养殖客户服务 | 投苗计划 → 苗种交付 → 放养与投喂 → 水质及健康观察 → 起捕销售 → 养殖周期复查 | 养户是否能够获得合理收益？需求减少涉及季节、行情还是产品效果？ | 品种、塘口、养殖批次、苗料及动保使用记录、技服反馈、销售与回款 |
| 种苗经营 | 育种与测试 → 繁育 → 批次检验 → 运输交付 → 客户放养 → 生长反馈 | 苗种交付是否匹配养殖窗口？异常反馈是否集中于同一批次？ | 品种与批次、可供数量、预订、检测、运输、接收记录及相似条件下的表现 |
| 动保与技术服务 | 现场发现问题 → 采集资料 → 专业人员核查 → 确认服务措施 → 执行记录 → 复查 | 哪些问题跨区域出现？专家和服务资源是否足够？ | 观察与诊断分别记录，关联样本、专业意见、服务措施、执行和复查结果 |
| 生猪合作养殖 | 批次计划 → 仔猪与投入品安排 → 农场饲养 → 生长及健康跟踪 → 出栏 → 合作结算 | 成本变化来自仔猪、饲料、养殖效率还是销售价格？ | 合作关系、批次成本、投入品、存栏与转群、出栏计划、费用归属和结算状态 |
| 禽类与反刍客户服务 | 客户生产计划 → 分阶段供料 → 饲喂反馈 → 肉用出栏或蛋奶产出 → 效果复查 | 不同动物和生产阶段的需求变化是什么？哪些客户需要服务支持？ | 肉鸡、肉鸭、蛋禽、牛羊分别定义指标，保留客户用途、日龄或阶段及产出资料 |
| 公司水产养殖 | 养殖单元与批次计划 → 苗料投入 → 环境与设备巡检 → 生长跟踪 → 起捕与销售 | 单个周期的产出、投入与资金占用怎样？设备事件会影响什么？ | 自营主体、养殖单元、批次、能耗、人工、投喂、环境、产量与单位成本 |
| 食品与供应追溯 | 原料接收 → 加工批次 → 检验 → 仓储运输 → 交付 → 客诉核查 | 反馈涉及哪些批次、客户和未交付订单？当前由谁负责？ | 原料与加工批次关系、检验状态、库存、运输条件、客户反馈与处置材料 |
| 海外经营 | 本地市场需求 → 本地供应与生产 → 技术服务 → 交付回款 → 扩产或资源复查 | 增长受市场、产能、服务资源还是资金限制？ | 国别与法人、品种、币种、时区、交付、产能、团队、资源申请及有效规则材料 |
| 研发与产品应用 | 业务提出问题 → 试验设计 → 对照与观察 → 专业评审 → 应用版本 → 使用反馈 | 哪些研发成果解决了客户问题？推广需要哪些条件？ | 试验对象、条件、样本与观察期、评审意见、应用版本和现场反馈 |

食品、反刍及不同养殖主题采用各自业务资料与角色设定。文档不据此推定所有品类均采用相同经营方式，也不推定全部客户养殖数据已经接入企业系统。

上游农业信息作为采购和成本研究输入。演示可以配置玉米、豆粕、鱼粉等原料的产地供给、收获季节、天气、运输与报价变化，再关联企业合同、库存和实际耗用。作物产区的天气消息只有经过供应关系及时间范围核查，才能用于说明具体采购影响。

老板每次查看经营专题，需要能够沿着同一事项继续查询：客户或生产发生了什么变化，影响了哪些供销和财务记录，负责人已经采取什么措施，仍需本人决定什么。影响路径是待验证的业务假设；只有取得对应证据，才能形成确定的原因解释。

## 4. 从老板与秘书的工作考虑需求

### 4.1 使用主体与信息来源

| 对象 | 在本产品中的身份 | 输入或结果 | 操作范围 |
|---|---|---|---|
| 老板 | 唯一业务使用者 | 目标、关注事项、交办、决定和个人记忆 | 查询、交办、确认、取消、调整目标、管理本人资料 |
| 老板 Agent | 受老板授权的执行服务 | 回答、会议材料、草稿、提醒及工具结果 | 在老板授权内读取资料和执行工具，正式状态由业务服务校验 |
| 技术维护者 | 管理后台使用者 | 模型、工具、模拟数据、场景和运行记录 | 配置和检查系统；无默认业务决定权及私人正文访问权 |
| 外部联系人与资料作者 | 模拟业务资料中的对象 | 汇报、回复、专业意见、期限申请和完成证据 | 通过模拟接口形成输入，保留作者、时间、来源与有效版本 |

外部联系人的身份用于辨认收件人、责任和材料出处。其反馈由模拟中心注入，经接口进入老板 Agent；整个演示能够由老板入口和技术维护入口完成。

产品经理、技术负责人、交互设计师、评测人员和面试官是建设与评审视角，不因此增加应用中的业务账号。这些视角的关注内容见第 4.7 节。

### 4.2 完整秘书场景

| 场景 | 模拟提问或交办 | 需要关联的材料 | 希望得到的结果 |
|---|---|---|---|
| 晨间安排 | “今天有哪些事情需要我亲自处理？” | 日程、待决定事项、承诺、经营事件、截止时间 | 今日清单、排序原因、准备材料和可执行动作 |
| 实时经营关注 | “今天哪些经营变化值得我过问？” | 指标、目标、更新时间、异常、责任人 | 数值与趋势、异常依据、关联事项和追问建议 |
| 经营解释 | “销售增长了，为什么毛利没有一起增长？” | 销售明细、产品结构、价格、成本、期间 | 可核算的变化贡献、未解释部分、核查问题 |
| 会前准备 | “下午和海外业务负责人谈什么？” | 联系人、历史会议、承诺、最新汇报和指标 | 会前材料、需要决定的问题、未完成事项 |
| 会后处理 | “根据这些记录整理决定和交办。” | 会议记录、参会人、相关任务 | 可确认的纪要、责任人、期限、后续检查方式 |
| 承诺与督办 | “上次交代的事情现在怎样？” | 本人交办、本人承诺、对方回复、完成证据 | 进展、逾期原因、待确认结果和催办草稿 |
| 文件与审批 | “这件审批为什么需要我确认？” | 申请、附件、历史版本、依据、金额 | 决策摘要、差异、缺少材料、确认后的模拟操作 |
| 沟通与关系 | “哪些重要回复还在等待我处理？” | 收件箱、联系人、历史沟通、本人表达要求 | 待回复清单、回复草稿、联系人背景 |
| 战略与行业研究 | “原料价格和海外市场有哪些变化？” | 公开信息、模拟行业信息、本人的关注主题 | 有日期与出处的材料、业务联系、待核查假设 |
| 人员与组织沟通 | “与这位负责人会面需要准备什么？” | 获准工作记录、目标、交办和历史承诺 | 工作事实、沟通问题、等待本人判断的内容 |
| 出行与接待 | “明天的行程和会面准备得怎么样？” | 日历、地点、时区、交通、预订、天气 | 行程安排、时间冲突、所需资料、变更影响 |
| 私人安排 | “把私人安排和工作时间协调一下。” | 本人主动提供的私人日程与可见范围 | 私有提醒、冲突提示、获准共享的时间范围 |
| 长期决定与学习 | “上次为什么这样决定，条件变化了吗？” | 决定、依据、当时假设、后续结果 | 历史依据、条件变化、本人确认后的更新 |

“秘书全面考虑”同时包含业务、沟通、时间和个人控制。Demo 通过一个连续工作日连接这些能力；每类能力都有相应模拟数据和工具输入。核心演示过程集中展示经营关注、会前准备、交办跟进、记忆以及后台配置。

语音交办需要实际语音转写服务和结果确认。文字交办与语音转写后的文本进入同一任务处理过程。语音服务单独记录启用状态与费用。

### 4.3 老板视角的具体关注

- 信息进入本人面前时，能够解释为何与当前目标、会议、责任或期限有关。
- 回答经营问题时，能够继续查看明细和原始依据；没有依据的原因保持待核查。
- 事项跨越多次对话和多天时，仍可查询当前进展、责任人和历史决定。
- 主动提醒区分立即处理、定时汇总和暂不通知，并支持确认知晓、暂缓与关闭。
- 会议、事件、消息、决定与交办使用关联记录，能够恢复人与事项的上下文。
- 本人可以查看、修改和删除长期记忆，控制私人资料的访问及分享范围。
- 工作完成需要有产物或状态依据，消息草稿、已发送、已回复、确认完成分别表达。

### 4.4 董事长兼总裁视角

**模拟表达：**“让我知道哪些事情需要亲自判断，给出依据、可选动作和时间要求。已经有人负责的事项，告诉我进展和需要协调的地方。”

| 角色输入 | 演示设定 | 对 Agent 行为的影响 |
|---|---|---|
| 职责 | 战略关注、经营协调、重要事项决定，以及本人的时间和承诺管理 | 信息需要关联目标、授权和本人需要作出的选择 |
| 阶段目标 | 关注增长质量、经营现金、重点区域进展和已交办事项 | 简报排序依据可查看，不只按指标变化幅度排列 |
| 决策范围 | 本人会议与沟通安排、跨部门协调、已授权范围内的演示决定 | 工具检查动作范围，超出范围的事项保留为建议或待补充 |
| 下属分工 | 日常经营处置由指定负责人承担；老板查看异常、进展和资源请求 | 不因出现一条告警就自动向老板发送全部明细 |
| 阅读方式 | 默认先展示待决定、待协调、需要知晓；可以继续追问 | 简报有层次，详细资料通过对应引用查看 |
| 时间安排 | 演示默认采用晨间汇总和约定的进展复查时间；重要事件独立触发 | 固定汇总与事件提醒各自记录触发依据 |
| 个人记忆 | 目标、已确认表达要求、本人承诺和历史决定 | 短期交办不自动成为永久个人习惯 |

每项待决定内容需要说明：当前事实、资料截至时间、影响范围、已有处理人、可选动作、需要本人决定的内容，以及决定期限。未取得的材料保持明确的缺少状态。

模拟老板可以将同一事项设为立即关注、下次会议讨论或交由老板 Agent 定期跟进。该调整需要保存，并影响后续提醒；本人的暂缓指令不修改原始业务事件和真实期限。

**结果检查：**老板能够依据简报采取一个明确动作；继续追问时可以取得原始依据；没有需要本人介入的事件不会仅因数值变化而持续打扰。

### 4.5 老板 Agent 使用的外部工作材料

| 材料来源 | 模拟接口提供的内容 | 老板 Agent 的处理 | 呈现给老板的结果 |
|---|---|---|---|
| 日程与秘书资料 | 参会人、资料清单、准备期限与访问范围 | 检查缺少材料、历史承诺和时间变化 | 会前材料、准备事项及需要本人确认的安排 |
| 业务负责人反馈 | 措施、负责人、预计时间、依赖、资源请求和附件 | 关联原交办，检查反馈是否回答问题 | 进展、证据、待补充事项及需要本人处理的申请 |
| 财务说明 | 公式、明细、期间、单位、结算状态与调整说明 | 复算并检查口径和版本差异 | 有出处的数值、差异及仍需核查的原因 |
| 资料更新事件 | 发布时间、版本、缺少范围与访问属性 | 更新检索及关联材料的有效状态 | 当前版本、影响范围及需要重新核查的材料 |

业务反馈至少说明处理进展、已经完成的动作、当前障碍、预计完成时间和对应证据。“收到”“正在处理”“已提交结果”和“已确认完成”使用不同状态。

模拟接口提供延期申请时保留原期限与申请原因，老板确认后形成新期限。接口提供财务资料更新时保留有效版本与调整说明；已经形成的会议材料显示需要重新核查，不能悄悄替换历史引用。

老板 Agent 整理待确认的纪要和消息，发送或记录决定时采用老板已授予的范围。工作日历中的私人时间可以只共享占用状态，私人事项正文按授权控制。

### 4.6 老板交办、外部反馈与资料冲突

| 情况 | 需要核查的内容 | 交接与处理要求 |
|---|---|---|
| 老板 Agent 提交一项交办 | 是否有老板指令或已有授权，责任人是否唯一可识别 | 保存授权来源、收件人和模拟发送记录 |
| 接口返回负责人完成反馈 | 结果是否回答原交办，附件是否可读，老板是否确认 | 保存为已提交结果，向老板呈现证据，由老板确认完成 |
| 财务与业务汇报数值不同 | 期间、单位、范围、结算状态和版本是否一致 | 展示差异，向相应责任人核查；资料中的职位高低不替代计算依据 |
| 多人对截止时间表述不同 | 当前有效期限、变更授权、消息时间及任务版本 | 使用已确认的有效期限，其他意见保留为待处理申请 |
| 资料给出原因但没有证据 | 原文作者、假设、可验证明细和缺少的信息 | 区分人员判断与已确认事实，不能把假设写成确定结论 |
| 业务事件需要老板协调 | 影响范围、已有措施、负责人权限和需要的资源 | 提交具体协调请求，附相关业务与财务材料 |
| 维护人员需要定位问题 | 获准查看的日志范围、敏感资料访问条件 | 使用运行标识与错误记录定位，访问正文另行受控 |

交办与反馈通过同一批任务、消息和资料标识关联。模型组织给老板的表达，正式授权和老板任务状态由对应服务检查；外部专业进展保持资料来源属性。

### 4.7 产品建设与面试评审视角

| 视角 | 主要判断 | 对需求输入的具体要求 | 可交付的证明材料 |
|---|---|---|---|
| 产品经理与应聘者 | 选择的工作是否值得交给 Agent，功能是否服务面试目标 | 每项核心任务有原有处理过程、增加的帮助、完成结果和验证方式 | 任务价值表、演示记录、个人贡献说明 |
| 技术负责人 | 开源复用和自建业务的职责是否清楚 | 明确业务状态、记忆、调度、模型配置各由哪个组件维护；目标模型实际兼容 | 固定版本、集成验证、运行与状态查询记录 |
| 交互设计师 | 老板是否能快速理解并处理事项 | 结果有来源、状态、下一步动作；确认对象和执行后果清楚；随时可以继续追问 | 老板页面与后台的实际操作过程 |
| 评测人员 | 演示是否依赖固定问法，状态是否正确 | 独立检查事实和动作，增加未预先编排的输入与资料冲突 | 检查任务、实际结果、错误记录及再次验证 |
| 招聘面试官 | 候选人是否理解问题、取舍、接口和结果 | 能解释业务必要性、技术选择、模型差异、费用及作品适用范围 | 现场任务、源码与工具记录、明确的复用说明 |

交互上，老板查看业务事实、依据和动作；Provider、参数、索引与请求记录在维护页面管理。老板可以理解“资料尚未更新”或“发送未完成”，无需理解底层接口名称。

面试材料应明确个人完成的产品设计、模拟服务、业务工具、页面及验证工作，同时列出直接复用的开源能力。演示任务的收益记录采用实际观察结果，不能补充未经使用者验证的海大业务收益。

### 4.8 农业资料的责任人与来源

下表描述老板查询资料时需要辨认的责任人、来源及协调关系。岗位名称、人员数量及汇报关系由模拟资料提供；这些对象不创建本产品的业务账号或独立 Agent。

| 职责视角 | 需要提供的业务材料 | 需要协作的人员 | 提交老板的条件与内容 |
|---|---|---|---|
| 产品事业部负责人 | 品种目标、产品效果、客户结构、推广安排与跨区域问题 | 区域经营、研发、生产及服务人员 | 跨区域资源冲突或重要产品问题；提供影响、方案与所需决定 |
| 区域经营负责人 | 本地养殖周期、需求、渠道库存、销售、客户反馈与回款 | 产品事业部、工厂、技服与财务 | 目标变化涉及多方协调；明确当地事实、现有措施和资源缺口 |
| 采购与营养配方人员 | 供货与成本资料、替代原料的专业评估、有效配方版本 | 工厂、品管、研发与财务 | 供应或成本问题超出已有安排；附可选方案和验证状态 |
| 工厂与品质人员 | 排产、产能、原料检验、成品批次、异常与交付进度 | 采购、区域销售、技术及物流 | 多工厂协调、重要交付或质量事件；明确数量范围与处置状态 |
| 种苗人员 | 繁育计划、检验、交付批次、客户接收与生长反馈 | 技服、销售、研发与品质 | 批次问题影响多个客户或投苗窗口；附追溯关系和待核查事项 |
| 技服与动物健康专业人员 | 现场观察、采样、检测、专业意见、服务与复查记录 | 养户、种苗、动保、饲料及研发人员 | 出现跨客户共同问题或专业资源不足；明确已确认与待确认信息 |
| 养殖运营与合作农场人员 | 批次投入、生长、健康、设备、出栏及结算资料 | 生产资料供应、兽医、财务与销售 | 周期经营结果变化或跨部门资源请求；说明归属主体与预计影响 |
| 禽类及反刍业务人员 | 生长或产蛋、产奶阶段、供料、产出及客户服务记录 | 产品、营养、技服与区域负责人 | 品种和阶段层面的共同问题；提供可比条件及样本覆盖 |
| 海外负责人 | 本地订单、生产、团队、回款、汇率口径与国别资料 | 集团产品、采购、财务及专业人员 | 跨国家资源、产能或资金安排；说明本地时间、选项与期限 |
| 食品与供应质量人员 | 批次关联、检验、仓储运输、客诉及处置意见 | 上游养殖、加工、物流及客户人员 | 重要质量事项或跨单位追溯；附已确认范围与专业处置意见 |

同一事件设置一名统筹负责人，可以关联多名材料提供人和专业核查人。统筹负责人负责组织反馈，专业判断保留签署人员与证据；相关人员的回复不会自动互相覆盖。

例如，养户报告生长异常时，技服提供观察，品管核查饲料批次，种苗人员核查苗种交付，专业人员判断健康因素，财务估算相关订单和应收影响。Agent 整理这些材料之间的共同信息与冲突，老板处理其中需要跨职责协调的事项。

## 5. BI 应关注什么，以及“实时”如何演示

### 5.1 经营指标输入

这些指标是围绕老板职责提出的演示候选。公式、数据责任人和提醒阈值采用明确标记的演示配置。

| 指标或主题 | 老板可能提出的问题 | 数据定义与计算注意点 | 可关联的秘书动作 |
|---|---|---|---|
| 饲料销售量与目标进度 | 哪个区域、产品影响目标完成 | 明确吨数、发货或结算时点、退货、内部交易、目标版本 | 准备经营会议问题，交办负责人说明 |
| 营业收入与结构 | 增长来自数量、价格还是结构 | 保持期间、业务范围、币种一致；贡献分析要有明细支持 | 形成对比材料，关联区域汇报 |
| 毛利率与单吨毛利 | 收入增长是否带来相应利润 | 毛利率使用总毛利 / 总收入；单吨毛利使用匹配业务毛利 / 吨数 | 提出价格、成本和结构方面的核查问题 |
| 现金与应收 | 资金是否充足，哪些回款需要关注 | 可用余额说明受限资金；逾期比例说明到期日、账龄、争议款 | 准备财务沟通和催办事项 |
| 原料采购与库存 | 哪些原料存在价格或供应压力 | 区分现货、期货、采购合同、在途、可用库存与日均耗用 | 汇总采购风险，关联供应会议 |
| 生产与交付 | 停产、产能或交付变化会影响什么 | 区分计划与实际、设备事件与已确认影响 | 提醒关键事件，查询处理责任人 |
| 质量与重要客诉 | 哪些事件需要本人介入 | 说明事件级别、确认状态、影响范围与当前处置 | 准备事件材料、更新交办和反馈 |
| 海外业务与汇率 | 区域经营变化是否来自汇率 | 区分本币与人民币，记录汇率日期及可比口径 | 准备跨时区会面和风险追踪 |
| 养殖相关经营 | 成本、行情和经营结果如何变化 | 生猪、水产等业务分别定义，不能混用饲料业务指标 | 形成专题材料及会议议题 |
| 战略重点与重大事项 | 重要目标有哪些进展和阻碍 | 使用里程碑、责任人、期限与完成证据 | 跟进本人交办和待决定事项 |

聚合百分比需要使用对应分子、分母重新计算；不能直接平均区域比率。同比、环比和预算差异采用匹配期间。目标进度考虑季节性或已配置的进度曲线。原料市场报价变化与企业采购成本变化分别说明。

### 5.2 每次 BI 回答需要携带的信息

| 信息类别 | 输入内容 |
|---|---|
| 指标定义 | 名称、业务含义、公式、单位、定义版本 |
| 查询范围 | 企业、组织、区域、产品、期间、币种、筛选条件 |
| 比较依据 | 同比或环比期间、目标版本、原始精度 |
| 数据时间 | 业务截至时间、来源更新时间、读取时间、模拟时钟 |
| 数据质量 | 缺少范围、结算状态、延迟状态、来源错误 |
| 数据出处 | 模拟接口与数据集版本，或者公开资料和原文位置 |
| 后续处理 | 异常规则、责任人、关联会议、已有交办和可选动作 |

计算由数据库查询或确定性工具完成，LLM 负责理解问题、选择工具、解释结果和组织后续动作。没有足够明细时，回答包含可确认的变化和仍需补充的信息。

### 5.3 更新频率与提醒

| 信息类型 | 演示中的更新时间方式 | 用户看到的说明 |
|---|---|---|
| 重要经营事件 | 在后台触发一个事件，事件立即进入规则判断 | 事件发生时间、收到时间、确认状态和通知状态 |
| 经营指标 | 配置按分钟刷新，或通过模拟时钟推进触发更新 | 数据截至时间、刷新时间、模拟标记 |
| 每日经营汇总 | 模拟日结后生成对应日期的数据 | 覆盖日期、已完成范围、尚未更新范围 |
| 财务结算与公开披露 | 根据报表期间和发布时间提供资料 | 结算或披露期间，不显示成分钟级经营数据 |
| 日程与任务 | 根据期限、日程变更和回复事件触发 | 到期原因、关联事项、本人可执行动作 |

实时 BI 的演示含义是：模拟来源更新后，系统实际获取变化、判断规则、更新页面并产生通知记录。演示时可以加速模拟时间，记录中的真实运行时间和模拟业务时间分别保存。

提醒配置包括阈值、持续时间、恢复条件、重复合并、冷却时间、免打扰时段、重要事件升级和提醒对象。提醒到达后，本人可以确认知晓、暂缓、加入会议、交办核查或关闭。

### 5.4 同一经营变化如何进入不同角色的工作

通知判断同时考虑影响、时间、资料可信程度、已有处理人、授权范围和是否需要本人决定。数值阈值用于发现变化，角色规则决定后续处理方式。

| 演示情况 | 负责人需要处理什么 | 老板收到什么 | 进入条件与结束依据 |
|---|---|---|---|
| 某工厂库存减少，负责人已有有效补货安排 | 业务负责人跟进到货，数据人员更新状态 | 需要时在汇总中查看，不产生重复催办 | 原有措施足以满足需求；到货与库存恢复可以查询 |
| 库存问题影响多个区域，解决需要跨部门资源 | 业务负责人提交影响、措施和具体资源请求 | 待协调事项、可选动作、需要决定的时间 | 已有处理方案无法在负责人权限内完成；协调结果与后续任务关联 |
| 毛利率下降达到演示阈值，资料完整但原因未解释 | 财务核对口径，业务负责人说明价格、成本和结构 | 经营关注项及核查进展 | 示例阈值为下降至少 1.5 个百分点；仅为可调整演示值 |
| 同一毛利变化已经有解释和执行安排 | 业务负责人按期更新措施，财务检查后续结果 | 在约定时间收到进展，出现新影响时更新 | 相同事件合并；措施、期限或影响变化时重新判断 |
| 重要质量事件已确认，需要本人协调 | 负责人提交已确认事实、处置和协调请求 | 按已设定的升级规则发送即时提醒 | 已确认级别、影响及所需决定满足规则；恢复后提供结果 |
| 重要风险消息尚未核实，但已满足待核实风险升级规则 | 指定人员尽快核查来源与影响 | 明确标注待核实的风险提醒和核查责任人 | 不把传闻写成事实；核实结果形成后续更新 |
| 某地区数据尚未同步 | 数据人员检查更新计划和失败原因 | 覆盖范围与截至时间说明 | 不完整数据不自动形成该地区经营为零的结论 |
| 交办临近期限且已有正常进展 | 秘书汇总，业务负责人继续执行 | 在约定汇总中看到进展 | 未达到已授权升级条件时不重复打扰 |
| 交办逾期且影响老板已确认的会议决定 | 秘书核查，负责人说明障碍和延期申请 | 待决定事项，保留原期限和申请理由 | 老板或指定授权人处理后更新任务版本 |
| 与本人目标相关但暂无行动要求的行业信息 | 秘书整理来源与业务联系 | 进入定期研究材料 | 出现具体影响或本人追问时形成进一步任务 |

所有数字阈值、事件级别和提醒时段均为模拟配置。界面需要能够查看触发依据、规则版本和责任人。相同数据变化在不同授权条件下可以产生不同通知结果。

### 5.5 “为什么需要我处理”的回答结构

经营关注卡片需要表达五项内容：发生了什么、可能影响什么、谁已经在处理、当前还缺少什么，以及为什么需要老板参与。可能影响必须注明证据或估算条件。

老板能够选择继续查看依据、请负责人核查、加入会议、授权既定动作或暂缓处理。本人选择只改变相关工作状态，不改变原始指标和历史记录。

### 5.6 农业指标、比较范围与数据时间

以下为演示指标输入。每项公式、观察方法和时间要求需要进入后台指标字典，不能直接标成海大的内部考核口径。

| 业务主题 | 需要支持的指标或事实 | 比较与计算要求 | 时间与数据限制 |
|---|---|---|---|
| 饲料供销 | 外销量、内部耗用、产品结构、单吨毛利、交付完成量 | 区分品种、阶段料、区域和外部客户；集团汇总采用明确的内部交易处理 | 订单、发货、签收与结算分别标识 |
| 需求与季节 | 已确认订单、养户计划、渠道库存、预计需求 | 按品种、地区、养殖阶段和季节曲线比较，保留预测版本 | 投苗计划与预计投喂不能冒充已执行需求 |
| 原料供应 | 合同数量、在途、验收合格可用量、预计耗用与交期 | 库存按批次、质量状态和使用限制计算；覆盖天数说明耗用假设 | 当日行情、合同价格、入库成本与生产领用成本分别表达 |
| 工厂运营 | 可用工时、排产量、完成量、关键工段负荷、换产与交付等待 | 产能利用率明确设备和产品范围；不同工艺产品不能直接共用额定产能 | 事件可以即时更新，产量和成本依据结算或汇总时间 |
| 水产养殖 | 投苗、存塘估算、投喂、生长、成活估计、起捕与养殖周期收益 | 比较同品种、相近规格、密度、环境和周期；混养、分批起捕与转塘单独记录 | 存塘和未完成周期收益通常包含估计，显示估计方法与观察日期 |
| 种苗 | 预订、合格可供量、批次交付、运输损耗、接收与生长反馈 | 批次出苗、客户接收与后续成活分别定义；客户条件影响后续结果 | 部分客户回访结果不能代表整个批次或全部客户 |
| 动保与技服 | 服务覆盖、问题响应、检测、专业确认、措施执行及复查 | 产品销量、服务完成、动物健康结果分别评价；注明观察人数或养殖单位数 | 服务完成当日可能尚无足够时间确认养殖结果 |
| 生猪养殖 | 存栏、转群、日增重、料重比、出栏、成本和周期结果 | 同批次或明确可比群体；仔猪、饲料、服务、人工等费用归属完整 | 期间利润、批次预计结果和已结算结果分别表达 |
| 禽类与反刍 | 肉禽体重与出栏；蛋禽产蛋及合格蛋重；奶畜产奶；肉用牛羊生长 | 单位分别使用头、羽、公斤等；肉用、蛋用、奶用对应不同投入产出指标 | 日龄、泌乳或产蛋阶段及观察期必须匹配 |
| 养殖客户经济结果 | 收获收入、投入品、人工、能耗、运输等成本与现金安排 | 区分养户预计收益、已结算收益、海大对应销售及应收 | 客户自报或部分样本需要显示覆盖比例和缺少项目 |
| 食品与质量 | 批次检验、追溯完整度、待交付量、运输记录、客诉及处理 | 问题批次与可能关联批次分别标记；数量关联需要真实记录支持 | 待检、已检与专业结论的生效时间分别保留 |
| 海外与项目 | 本币经营、可比币种结果、交付、产能、资金占用、建设里程碑 | 记录国家、主体、汇率类型和日期；经营变化与折算影响分别计算 | 本地经营日期、集团汇总日期和资料有效期分别展示 |

比例使用相应分子、分母计算。饲料转化、生长与成活指标保留业务定义：转群、转塘、分批出售和补苗都可能改变统计范围；数据不足时不生成一个貌似准确的比率。养殖批次尚未结束时，显示阶段观察结果及估计状态。

客户经营和集团经营分别呈现。养户收益改善可以成为产品服务价值的观察材料；将其解释为海大收入、利润或回款变化，需要相应订单、交易和财务证据。内部供料的业务数量可以展示，集团合并收入按财务口径处理。

农业数据的“实时”按来源定义：设备采样、人工巡检、客户上报、订单和财务结算具有不同更新时间。界面同时说明观察时间、接收时间、有效覆盖及是否为估计；后台刷新成功不改变原始资料的观察时间。

### 5.7 老板的经营会议与农业周期

以下频率为演示配置，海大的实际会议节奏尚未取得。日程工具将业务复查时间关联到老板日历，后台可以修改。

| 经营时点 | 需要准备的材料 | 老板处理的事项 | 后续跟进依据 |
|---|---|---|---|
| 年度、季度或重点项目复查 | 品种与区域目标、资源安排、资金及建设进度 | 目标、资源和重要项目选择 | 有效目标版本、决定、负责人及里程碑 |
| 投苗、补栏或旺季准备 | 苗种、饲料、工厂、物流、服务人员和客户计划 | 跨部门供给冲突、重要准备不足 | 准备清单、需求版本和按期交付情况 |
| 每月经营复查 | 销量、毛利、费用、资金、客户效果与周期变化 | 增长质量与经营措施调整 | 财务核查、业务措施、后续检查日期 |
| 每周跨职责协调 | 订单、原料、排产、质量、技服和交办进展 | 资源请求、责任冲突和需要本人协调的事项 | 统筹负责人、承诺、执行记录 |
| 每日秘书汇总 | 重要事件、会前准备、本人承诺与待决定事项 | 当日需要本人处理的内容 | 日程、决定和任务状态 |
| 天气、供应或质量事件 | 发生区域、关联业务、确认状态、已有措施和专业意见 | 满足演示升级条件的跨区域协调或重要决定 | 事件恢复、专业复查和交办完成分别记录 |
| 养殖周期结束或产品试验复查 | 完整周期投入产出、对比条件、服务过程和结算 | 是否继续采用已有方案、是否要求进一步验证 | 专业评审、客户反馈及下一周期安排 |

会议材料需要区分“当天需要决定”和“本周期需要持续观察”。例如，服务人员已经提交复查安排，但养殖结果尚需观察，交办保留下一次检查时间，不因当天暂时没有新数据而反复催办。

## 6. Agent 方法：六个部分与运行条件

`Prompt + Workflow/SOP + Knowledge Base + LLM/DSLM + Tools + Evaluation` 是合理的能力组织方法。它可以作为本项目的建设依据；实际效果需要通过任务运行验证，不能仅凭具备这些组成就判断已经达到最佳实践。

Anthropic 的工程资料区分预先定义路径的 Workflow 与由模型动态选择步骤和工具的 Agent，并将检索、工具和记忆作为模型可使用的能力。本项目可以将固定业务步骤和动态工具选择结合使用。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

### 6.1 六个部分各自承担什么

| 部分 | 在本项目中的作用 | 具体输入或材料 | 后台需要管理什么 |
|---|---|---|---|
| Prompt | 定义秘书职责、沟通方式、来源要求和行动限制 | 系统提示、角色说明、回答模板、场景提示 | 内容、版本、适用任务、启用状态 |
| Workflow / SOP | 表达业务步骤、必要检查、确认节点和结束条件 | 晨间简报、异常处理、会议准备、会后交办流程 | 步骤、触发条件、工具引用、确认规则、版本 |
| Knowledge Base | 提供事实、制度、指标含义和业务材料 | 公开报告、合成制度、演示汇报、指标说明 | 文档、来源、版本、有效期、访问范围、索引状态 |
| LLM / DSLM | 理解交办、规划工具使用、总结解释和生成材料 | DeepSeek 配置、任务对应模型设置 | Provider、API 类型、模型标识、参数、能力、预算 |
| Tools | 获取数据、执行计算、更新事项和完成已确认动作 | BI、日历、联系人、会议、消息、任务、审批和模拟服务 | 请求定义、权限、连接、执行结果、超时及错误 |
| Evaluation | 检查事实、工具选择、动作、状态、速度和费用 | 演示任务集、预期事实、业务状态、实际运行记录 | 任务、数据集、模型版本、判定结果与运行详情 |

这里将 DSLM 理解为领域专用语言模型，属于可选能力。此次使用通用模型结合领域知识和业务工具，不要求训练海大专用模型。模型是否需要领域专用能力，应由具体任务的运行结果支持。

### 6.2 需要补充的运行能力

| 能力 | 对本产品的必要性 | 示例 |
|---|---|---|
| Agent Runtime | 管理模型与工具的多轮执行、流式输出、超时、取消和结束 | 查询指标后继续读取明细，再组织解释 |
| Personal Memory | 保存本人确认的工作目标、表达要求和历史决定 | 记住简报格式，修改后在新会话中采用 |
| Task State | 保存任务、审批和消息的正式状态 | “待确认”“执行中”“已发送”“等待回复”可查询 |
| Triggers / Scheduler | 支持时间、事件和数据变化触发任务 | 晨间简报、到期提醒、指标异常 |
| Permissions / Confirmation | 检查身份、工具范围和需要本人确认的动作 | 维护身份不能默认读取私人正文；发送使用老板的有效授权 |
| Observability | 记录工具、模型、数据版本、费用和失败位置 | 后台能够解释某次回答使用了哪些资料和操作 |

Knowledge Base 保存参考资料；Personal Memory 保存与本人持续工作相关的内容；Task State 保存当前业务状态。三者分别管理，查询时可以关联。

SOP 中固定的计算、授权检查、重复请求控制和状态更新由程序负责。模型可以在允许范围内决定需要查询哪些材料、选择什么工具以及如何表达结果。文档内容和工具返回内容按资料处理，不能改变系统权限。

Skill 可以将任务说明、SOP、工具使用说明、资料引用和检查方式组织在一起。Skill 更新需要记录版本并执行相应演示任务，不能仅凭内容生成完成就认为效果提高。

### 6.3 Evaluation 在 Demo 中如何使用

Agent 的检查需要同时观察输出文本、工具执行和环境中的最终状态。只检查回答是否流畅，会遗漏未保存事项、错误更新和重复动作等问题。[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

本项目采用固定演示数据集和明确检查点：数值可复算、来源可查看、动作有记录、更新可重新读取、错误场景有正确状态。模型输出措辞可以变化，关键事实和动作条件应保持一致。

### 6.4 不同任务需要哪些 Agent 能力

| 任务 | 程序负责的步骤 | 模型需要承担的工作 | 使用的知识与记忆 | 需要检查的增益 |
|---|---|---|---|---|
| 晨间安排 | 读取日历与任务，计算期限和时间冲突 | 结合目标、事项和会议组织当天关注内容 | 当前目标、阅读要求、历史承诺 | 是否减少查找和整理，并保留重要事项 |
| BI 连续追问 | 查询授权数据、执行公式、返回明细和时间 | 理解自然语言、选择维度、根据新问题调整查询、表达未知 | 指标定义、业务术语、当前关注主题 | 改变问法和查询维度后仍得到正确结果 |
| 经营异常跟进 | 检查规则、合并事件、保存任务和通知 | 综合多个来源，整理核查问题、解释与协调请求 | 组织分工、已有决定、相关会议 | 是否恢复完整上下文并提出有依据的下一步 |
| 会前与会后工作 | 查询关联资料、检查身份、保存确认结果 | 整理议题、识别承诺、组织纪要和交办草稿 | 历史会议、联系人、工作目标 | 是否减少遗漏，责任与期限是否准确 |
| 文件阅读和专题研究 | 检索资料、定位引用、保存版本 | 比较材料、解释联系、区分事实与推断 | 公开资料、合成制度、本人研究问题 | 是否保留出处并识别材料间的冲突 |
| 沟通、任务与审批 | 执行授权检查、写入动作、重新查询状态 | 理解交办、生成草稿、识别缺少的决定性信息 | 本人表达要求、联系人、已确认事项 | 是否减少人工重复组织内容，动作是否符合交办 |
| 日程、出行与私人安排 | 时间和时区计算、冲突检查、访问控制 | 结合会议目的整理准备事项与变更影响 | 本人安排要求、获准行程资料 | 是否完整说明影响，并保护私人内容 |

六个组成部分按任务需要参与运行。确定性计算可以直接调用工具；资料检索只在需要相应知识时执行。工具数量、模型轮数和使用组件数量均不作为功能效果指标。

### 6.5 原有处理过程与演示价值的比较

| 任务 | 人工基准过程 | Agent 增加的帮助 | 实际记录方式 |
|---|---|---|---|
| 准备经营会议 | 分别查看日程、汇报、指标和上次纪要，手工组织议题 | 按同一会议关联材料、承诺和待决定事项 | 记录准备用时、遗漏项、错误项和人工修改量 |
| 回答经营追问 | 打开报表、选择维度、确认口径、整理说明 | 理解连续提问，组织查询并引用依据 | 记录查询步骤、结果正确性、等待时间和修正次数 |
| 跟进老板交办 | 查找原消息、询问进展、核对附件并更新清单 | 保留任务上下文，关联回复和完成证据 | 记录查询次数、重复催办、状态错误与核查投入 |
| 处理临时变化 | 找出受影响的会议、人员、资料和任务，分别更新 | 根据关系识别影响，准备获准修改 | 记录遗漏、重复操作和重新整理所需时间 |

人工与 Agent 使用相同的模拟资料和完成标准。时间记录同时包含模型等待、人工核查和修改；如果 Agent 没有改善结果或耗费更多时间，应如实保留。该比较是演示评估，不代表海大真实工作效率。

### 8.2 nanobot：通过 Python SDK 接入专用产品

项目入口：[HKUDS/nanobot](https://github.com/HKUDS/nanobot)。

**个人 Agent 能力。** 项目包含聊天渠道、WebUI、TUI、文件与文档工具、Skills、MCP、记忆和自动任务。Python 要求为 3.11 或以上。它能够作为独立助理运行，也提供嵌入其他应用的 SDK。[官方 README](https://raw.githubusercontent.com/HKUDS/nanobot/main/README.md)、[包与依赖定义](https://raw.githubusercontent.com/HKUDS/nanobot/main/pyproject.toml)

**运行组织。** `AgentLoop` 负责会话与运行上下文，`AgentRunner` 负责模型和工具之间的执行循环，`ContextBuilder` 组织上下文。Tools、Provider、Channel、Plugin 和 MCP 各有扩展位置。对本项目而言，可以将 BI、会议和交办接成业务工具，并将运行事件送入管理后台。[Architecture](https://raw.githubusercontent.com/HKUDS/nanobot/main/docs/architecture.md)

**可核查的接入方式。**

| 官方入口或结果 | 对本项目的作用 |
|---|---|
| `from nanobot import Nanobot` | 在 Python 业务服务中使用运行服务 |
| `Nanobot.from_config()` | 加载指定的模型、工具、工作目录与运行配置 |
| `bot.run()` | 执行一项交办，取得结构化结果 |
| `bot.stream()` | 向老板页面与后台传递执行进展 |
| `session_key` | 组织会话历史 |
| `RunResult.content / tools_used / usage / stop_reason` | 显示产物、使用的工具、用量和结束原因 |

以上来自[Python SDK 文档](https://raw.githubusercontent.com/HKUDS/nanobot/main/docs/python-sdk.md)。v0.3.5 标签也提供相应 SDK 入口说明。不同会话标识只区分历史；工作目录、凭据和记忆的访问范围仍需按产品身份配置。SDK 观察事件不能替代工具执行时的权限校验。

**记忆与持续工作。** 记忆文档描述历史摘要及 Dream 整理机制，涉及 `USER.md`、`SOUL.md`、`MEMORY.md` 等内容。自动任务有独立配置与调度行为。仅嵌入 SDK 不代表后台调度已经运行；本项目需要明确哪个服务负责晨报、提醒和记忆整理，并处理重启后的任务状态。[Memory](https://raw.githubusercontent.com/HKUDS/nanobot/main/docs/memory.md)、[Automations](https://raw.githubusercontent.com/HKUDS/nanobot/main/docs/automations.md)

**HTTP 与模型。** 独立 HTTP 服务提供 `/v1/chat/completions`，会话由服务管理；接口响应、渠道消息排队和实际送达需要分别理解。HTTP 成功不能证明业务工具已经完成目标动作。Provider 配置支持模型与服务设置，但所选 GPT / DeepSeek 的 API 类型和能力仍需要按固定版本验证。[HTTP API](https://raw.githubusercontent.com/HKUDS/nanobot/main/docs/openai-api.md)、[Providers](https://raw.githubusercontent.com/HKUDS/nanobot/main/docs/providers.md)

**本项目可复用的内容：** 多轮工具运行、会话、Skills、MCP、记忆基础、模型配置与运行事件。

**本项目需要建设的内容：** 老板首页、BI 口径、模拟中心、本人事项、联系人关联、本人确认、维护访问范围和演示评测。应用负责维护老板正式业务状态，并将工具实际结果与模型回答对应起来。

**采用前应验证：** 固定版本能否完成 DeepSeek 工具调用；同初始资料的两次独立执行；工具事件和用量是否齐全；后台更新配置后是否生效；新会话是否正确使用已确认记忆；定时任务是否由唯一服务负责。

### 8.3 QwenPaw：在现有 Console 上增加老板业务能力

项目入口：[agentscope-ai/QwenPaw](https://github.com/agentscope-ai/QwenPaw)。历史 CoPaw 地址已经转向这一项目，版本资料需要使用当前名称与对应标签。

**个人 Agent 能力。** 官方资料提供多种消息渠道、文档处理、Skills、MCP、长期记忆、Cron 和 Heartbeat。支持云端、本地及自定义模型，列有 OpenAI 和 DeepSeek。项目使用 AgentScope 运行能力，Python 范围为 3.11 至低于 3.14，可通过 Python 包或容器部署。[README](https://raw.githubusercontent.com/agentscope-ai/QwenPaw/main/README.md)

**Console 管理范围。** 包含 Chat、Inbox、Channels、Sessions、Cron、Heartbeat、Files、Skills、Tools、MCP、Configuration、Models 和用量相关页面。Inbox 可承载待确认事项与调度结果；Cron 支持手动执行和暂停等管理动作；文件与记忆材料可以编辑。官方文档也介绍自定义 Console 静态目录与构建方式。[Console 文档源码](https://raw.githubusercontent.com/agentscope-ai/QwenPaw/main/website/public/docs/console.en.md)

这些管理能力适合演示 Agent 配置与运行过程。老板的指标解释、会议准备和交办状态仍需专用页面与业务对象。

**可核查的接入方式。**

| 官方接口元素 | 文档说明 | 对本项目的作用 |
|---|---|---|

| 审批 | 申请、附件、依据、版本、流程状态 | 确认、拒绝、补充材料、产生记录 | 待决定事项与授权操作 |
| 行业与外部信息 | 行情、天气、政策、区域新闻及时间 | 发布模拟信息、更新专题材料 | 行业研究与出行准备 |
| 知识资料 | 公开报告、合成制度、汇报、资料版本 | 导入、更新、撤销、提供原文 | 阅读、检索和依据查看 |
| 通知中心 | 提醒、渠道、送达与查看状态 | 生成、确认、暂缓、关闭提醒 | 主动工作与打扰控制 |

模拟消息的发送结果保存在模拟发件箱，后续可以查询；模拟审批操作更新审批记录。写入动作产生的状态需要进入后续查询和 Agent 上下文。

### 10.2 合成数据包

| 数据包 | 建议包含的内容 | 需要保持的关系 |
|---|---|---|
| 老板档案 | 演示身份、职责、目标、简报格式、关注主题、提醒时间 | 所有排序与个性化行为能够引用相应设置 |
| 人员与组织 | 1 位老板及秘书、业务负责人、演示客户、合作方等模拟联系人 | 联系人、会议、交办和消息使用稳定对象标识，联系人不具有登录权限 |
| 经营记录 | 多区域、多产品的销售、成本、目标、库存、应收和事件 | 明细汇总与看板数值一致，跨系统引用一致 |
| 时间范围 | 一段连续经营日期、对比期间和未来日程 | 可以演示同比或环比、期限、跨日和时区变化 |
| 会议材料 | 历史纪要、下一场经营会议、专题会、汇报和附件 | 历史承诺与当前任务关联，决定有明确材料来源 |
| 消息与任务 | 待回复、已回复、逾期、等待资料、等待本人确认等状态 | 发送、回复、事项更新能够相互查询 |
| 文件与知识 | 行业术语、演示制度、指标口径、资料及其版本 | 引用可以回到原文，资料变更影响后续检索 |
| 审批与决定 | 完整申请、缺少附件、版本变化、已确认和待确认记录 | 确认对象、内容版本和最终状态一致 |
| 出行与私人安排 | 工作行程、时区、地点、准备清单和私有安排 | 冲突能够被检查，可见范围符合演示角色 |

数据规模需要足够支持筛选、聚合和跨资料查询。建议演示数据包含数百条经营明细、数十项消息与任务，以及覆盖不同状态的会议和审批；具体数量由后台配置，不固定在页面代码中。

生成过程可以使用规则、模板和可配置随机 seed。金额、数量、比例、期间和实体关系由确定性逻辑校验；模型生成的叙述材料需要引用同一批业务事实。

所有合成人名、事件和内部决定标明演示属性。模拟资料中的正文指令仅作为材料内容，不能取得工具权限或改变系统行为。

### 10.3 数据一致性与时间控制

1. 每次演示指定数据集标识、版本、seed、业务起始时间和生成器版本。
2. 同一个组织、联系人、会议和任务在不同接口中使用相同标识。
3. 汇总数值由明细计算；经营解释能够查看相应维度或记录。
4. 同一次查询读取一致的数据版本；业务更新之后产生可辨识的新状态。
5. 使用业务时间推进事件，记录真实运行时间，二者能够同时查看。
6. 生成的数据可以重复；LLM 输出允许措辞变化，事实和动作通过相同检查。
7. 重置演示需要同步处理该数据集对应的事项、会话、记忆、定时任务和模拟发件箱。
8. 历史运行记录保留原有数据集与配置标识，不能被误认为当前场景的结果。
9. 重放写入请求采用明确的重复请求控制，不能因刷新页面或重新发送而重复创建事项。
10. 模拟接口错误在发生位置返回明确错误；本次任务记录失败或等待处理，不悄悄改用预设成功结果。

### 10.4 场景剧本

| 场景 | 后台设置或触发 | 期待 Agent 展示的行为 |
|---|---|---|
| 正常工作日 | 完整日程、资料、正常指标和待办 | 组织晨间安排，准备会议并处理交办 |
| 销量增长、毛利率下降 | 配置产品结构、售价和成本变化 | 查询并计算变化，区分已解释与待核查部分 |
| 区域目标进度不足 | 某区域低于演示进度曲线 | 判断持续条件，关联负责人和经营会议 |
| 回款或库存异常 | 逾期金额增加，或可用库存降低 | 给出依据，形成确认后的核查任务 |
| 重要质量事件 | 触发事件及连续处置更新 | 发出相应提醒，跟进责任人与状态 |
| 会议临时变化 | 调整会议时间或人员，附加新材料 | 更新准备清单，检查冲突和历史承诺 |
| 交办得到回复 | 模拟收到负责人反馈和附件 | 关联已有任务，提示核查，区分回复与确认完成 |
| 审批材料不足 | 缺少附件、金额说明或有效版本 | 指出缺少材料，保持待处理状态 |
| 数据不完整或过期 | 部分区域尚未更新，或来源时间较早 | 标识覆盖与时效，不把缺少数据当成零 |
| 工具不可用 | 接口超时、不可用或请求错误 | 记录明确错误，终止依赖该结果的动作 |
| 权限不满足 | 技术维护身份访问私人正文，或请求未获老板授权的业务动作 | 拒绝相应操作，并保留可检查的结果 |
| 重复与并发变化 | 重复提交，或确认前资料版本改变 | 保持单次业务结果，检查当前版本 |
| 记忆修改 | 更改简报格式、目标或提醒要求 | 后续任务使用当前有效设置 |

这些剧本用于安排数据和事件。系统不能按场景名称直接返回预设最终答案。

### 10.5 评测人员视角：未预先编排的输入

场景管理保存的数据标签和预期检查用于后台评测。Agent 读取的业务接口只返回角色有权访问的事实、说明和来源；预期答案、评分规则和带有结论的场景名称不进入模型上下文。

| 变化方式 | 示例输入 | 需要观察的行为 |
|---|---|---|
| 改变表达和查询维度 | 从地区分析改为产品分析，随后更换可比期间 | 使用新的参数重新查询，保持单位和期间一致 |
| 增加同名或相近身份 | 两位同名负责人涉及不同业务 | 利用已有上下文辨认；无法确定时请求必要信息，不猜测收件人 |
| 引入资料冲突 | 汇报的毛利与同期间财务明细不一致 | 查看口径和版本，保留冲突，不能平均数值或按身份高低选择答案 |
| 缺少原因依据 | 提供销量与毛利汇总，但没有价格和成本明细 | 解释已知变化，明确不能确定具体原因 |
| 改变状态顺序 | 负责人回复到达后，老板撤回该交办 | 使用当前有效状态，后续不继续发送相关催办 |
| 改变资料版本 | 用户确认草稿前，金额或收件人发生变化 | 识别确认内容已变化，重新核查适用授权 |
| 同时发生多个事件 | 毛利变化、会议改期和回复到达 | 关联已有事项，避免分别创建重复任务 |
| 工具写入后模型出错 | 任务已保存，后续模型调用失败 | 保存已执行动作的实际状态，不能宣称从未执行，也不能重复写入 |
| 文档含有越权操作内容 | 汇报中要求读取私人资料或更改权限 | 将正文当作资料，工具权限检查继续有效 |
| 重置后重新运行 | 同一场景更换数据集版本 | 当前任务使用当前材料，历史记忆与结果不会混入 |

评测任务可以由演示者临时选择参数和事件组合。预期数值由独立的明细复算得到，预期动作由已设定的授权与任务状态判断。模型评语只能作为辅助材料，不能单独判定数字、权限和业务写入是否正确。

### 10.6 农业业务的模拟资料与接口能力

以下资料通过第 10.1 节的模拟服务提供，复用现有查询、事件、材料和任务能力。它们支持老板个人秘书的追问与交办，不要求为每个主题建设完整的独立业务应用。

| 模拟资料域 | 接口需要提供的内容 | 需要保持的关联 | 可配置的变化 |
|---|---|---|---|
| 产品与组织 | 产品事业部、区域、法人、工厂、服务站、负责人和职责有效期 | 同一记录可按产品、区域和法人查询，避免重复累计 | 负责人变更、跨区域共同事项、授权变化 |
| 养户、渠道与合作关系 | 养户、经销商、服务人员、合作农场、公司养殖单位及关系类型 | 付款客户、产品使用者、资产归属和费用承担方分别明确 | 客户自报延迟、经销库存变化、合作结算争议 |
| 动物、阶段与养殖批次 | 品种、用途、生长阶段、塘口或栏舍、批次、投苗或补栏及转移 | 一个地点可有多个养殖周期；混养或跨批次转移有独立记录 | 周期延期、分批起捕、转塘转群、补苗及阶段变化 |
| 原料、配方与生产 | 原料批次、检验、库存、合同、配方版本、生产批次、工段和排产 | 原料使用量、配方生效时间、生产与成品批次可相互查询 | 到货延期、待检库存、原料涨价、产能限制或交付变化 |
| 种苗 | 品种、繁育批次、检验、预订、运输、接收和客户回访 | 苗种批次与养殖批次形成明确关系，数量和单位一致 | 集中反馈、运输影响、订单超过可供量、回访覆盖不足 |
| 养殖观察与技服 | 投喂、水质或环境、设备、健康观察、检测、专业意见与服务记录 | 记录观察者、位置、时间、方法和适用批次 | 天气变化、采样中断、人工修正、待确认健康问题 |
| 动保产品与使用资料 | 产品批次、库存、获准方案、使用记录、服务与复查 | 专业意见、执行者、对应批次与实际执行状态关联 | 专家资源不足、执行记录缺少、复查结果尚未形成 |
| 养殖成本与销售 | 投入品、费用、起捕或出栏、销售、周期结算和预计结果 | 同一批次成本归属明确；客户自报数据与企业账目分别保存 | 行情变化、成本未结算、分批出售、预计与实际结果变化 |
| 食品与追溯 | 原料来源、加工批次、检验、仓储运输、销售与客诉 | 批次的投入产出及客户流向可以查询；缺少关系保持缺少状态 | 待检批次、追溯资料不足、运输异常、专业处置进展 |
| 海外与研发项目 | 国别、主体、币种、时区、产能项目、试验及评审资料 | 项目、资源请求、人员、阶段结果与老板决定关联 | 本地需求变化、产能延期、资料有效期变化、试验条件差异 |

农业观察记录需要保留 `observed_at`、`received_at`、`valid_from`、`source_type`、`measurement_method`、`coverage` 和 `estimation_status` 的信息含义，最终字段命名在工程设计时确定。模拟观察时间与程序真实执行时间继续分别保存。

`PUBLIC_SOURCE` 中的年报事实保持其披露日期。演示中的塘口、农场、疾病事件、客户、业务数据与内部处理记录均属于 `SIMULATED`，不得使用真实人员姓名构造未公开的经营事件。

### 10.7 农业数据关系与后台配置要求

后台需要能够配置业务事实及其关联，不能只配置预期回答。农业数据包至少包含：一种水产品种的完整客户服务过程、一组生猪合作批次、一组禽类客户记录、一组种苗与动保关联记录，以及海外、食品和研发专题所需资料。反刍业务提供可独立查询的客户与阶段指标。

| 配置对象 | 后台需要支持的操作 | 检查内容 |
|---|---|---|
| 业务归属 | 指定客户、合作农场或公司养殖关系，维护法人及交易关系 | 养殖资产、成本、收益和应收归属一致 |
| 品种与阶段 | 选择动物品种、用途、生长阶段、单位与适用指标 | 不能把肉禽、蛋禽和奶畜指标混用 |
| 农业周期 | 配置投苗补栏、观察、起捕出栏、结算及季节曲线 | 模拟时钟推进时，事件顺序及比较期间有效 |
| 批次追溯 | 关联苗种、原料、饲料、动保、养殖及加工批次 | 查询能回到实际关联记录，不按相似名称推定关联 |
| 数据质量 | 配置客户上报范围、估计方法、延迟、缺少及冲突记录 | 缺少值不会变成零，局部样本不会成为全量结论 |
| 指标与影响测算 | 保存公式、单位、范围、比较条件、假设和版本 | 确定性计算能够复算，条件变化后重新计算 |
| 农业事件 | 设置影响区域、关联对象、观察证据、专业确认与处置进展 | 天气或行情信息只有匹配业务对象后才能产生具体影响说明 |
| 职责与升级 | 设置统筹人员、材料责任、专业确认人、老板参与条件和复查时间 | 业务处理、专业判断与老板决定分别记录 |

养殖数量采用期初、增加、转入、转出、出售、损耗和期末之间的平衡检查；估计数量允许附明确误差范围，不能为了平衡而自动补造交易。饲料库存、投喂、生产耗用和养殖产出分别计算，不能使用简单的质量相等关系替代生物生产过程。

影响测算只使用已配置的公式和假设。例如，订单交付影响可以依据已确认订单、可用库存和有效排产计算；养户未来收益需要完整收入成本假设。缺少必要资料时，输出“待补充材料”及具体项目，不生成预设损失金额。

接口权限支持查询、材料整理、任务建立、模拟通知与既定授权审批。配方发布、用药方案、设备控制、质量放行、采购成交及资金交易由专业业务流程承担；演示中由有职责的合成人员提供相应状态，Agent 读取状态并跟进本人已授权的协调事项。

## 11. 老板入口与管理后台的范围

### 11.1 老板入口

| 页面或入口 | 需要呈现的内容 | 主要动作 |
|---|---|---|
| 今日工作 | 日程、待决定、重要异常、待回复、等待反馈 | 查看依据、调整优先次序、交办、确认和暂缓 |
| 聊天交办 | 连续对话、执行进展、引用资料、任务产物 | 追问、补充、确认、取消、打开结果 |
| 经营关注 | 关注指标、趋势、来源、时效、异常及关联事项 | 查询维度、查看明细、形成会议问题或任务 |
| 会议与资料 | 会前材料、历史会议、联系人、文件与决定 | 准备会议、阅读、确认纪要与交办 |
| 任务与承诺 | 本人任务、他人交办、等待回复和完成证据 | 查询、调整期限、催办、取消、确认完成 |
| 通知与设置 | 提醒、本人目标、长期记忆、授权和私人范围 | 修改、暂停、删除、控制可见范围 |

聊天与页面共享正式业务状态。老板从回答中创建的事项能够在任务页面查看；后台修改的规则能够影响下一次主动任务。

### 11.2 管理后台

| 管理区域 | 需要配置或查看的内容 | 对演示的作用 |
|---|---|---|
| 老板档案与访问配置 | 老板档案、目标、本人授权、私人范围和技术维护权限 | 为唯一老板提供个人上下文，明确维护权限 |
| 模拟接口中心 | 系统与接口目录、请求响应定义、连接状态、人工调用 | 无企业内部接口也能实际执行工具 |
| 模拟数据集 | seed、数量、期间、关联关系、版本、生成及重置 | 可复现演示业务环境 |
| 场景与事件 | 正常和异常配置、模拟时钟、事件触发、回复生成 | 控制演示节奏，验证主动工作 |
| Prompt | 秘书职责、表达要求、场景提示、版本 | 配置模型行为并检查变更效果 |
| SOP 与 Skills | 任务方法、步骤、输入输出、工具范围、启用状态 | 表达可复用工作方法 |
| Knowledge Base | 文档、来源、分类、有效期、权限、索引与检索检查 | 让资料能够被查询并显示依据 |
| 模型与 Provider | DeepSeek 配置、API 类型、能力、参数、费用 | 修改配置并核查实际调用 |
| Tools 与连接 | 工具说明、参数、模拟接口映射、权限和超时 | 管理模型可执行的业务能力 |
| BI 与提醒规则 | 指标定义、维度、刷新、阈值、持续和恢复条件 | 使经营查询和通知采用同一口径 |
| 会议、联系人、事项 | 老板相关对象、模拟联系人、关联关系、状态与历史 | 检查老板 Agent 的执行结果及模拟输入 |
| 记忆与个人设置 | 内容、来源、确认状态、有效期、可见范围 | 修改后验证新会话行为 |
| 任务调度 | 时间、事件条件、时区、暂停、取消及手动执行 | 实际运行晨报、到期与事件任务 |
| 动作确认记录 | 老板授权的对象、内容、版本、确认状态和执行结果 | 检查审批、发送及日程更新的授权依据 |
| 运行与用量 | 模型、工具、参数、结果、耗时、Token、错误、配置版本 | 解释每项任务如何完成 |
| 演示评测 | 场景、数据集、检查项、模型配置、结果和记录 | 对比运行结果并定位问题 |

页面操作需要对应真实保存的服务端状态。加载、空内容、运行中、完成、失败和无权限状态均需明确。配置内容保存后可以重新读取，启用后影响实际运行。

模型内部推理不作为审计材料。后台记录可观察的工具选择、调用参数、返回结果、动作和状态变化，并控制资料正文与凭据的可见范围。

### 11.3 模拟中心的操作体验

管理人员能够通过页面选择数据集，生成或载入业务材料，选择场景，检查接口返回，启动一次 Agent 任务，并查看同一任务的模型调用、工具调用和业务结果。

支持在任务进行中注入允许的业务事件，例如收到回复或新增会议材料。重复演示时可以重置场景；需要比较模型时可以使用相同初始数据集分别运行。

场景成功与 Agent 成功分别记录：接口按设定返回不可用，说明模拟场景执行符合设置；Agent 是否正确说明问题、停止相关动作，需要单独检查。

### 11.4 老板与技术维护的权限

| 操作 | 老板本人及其授权的 Agent 执行 | 技术维护身份 |
|---|---|---|
| 查询本人工作信息 | 在本人可访问范围内查询和整理 | 仅检查获准运行信息，正文另行授权 |
| 查看私人事项正文 | 本人查看；工具在相应授权内读取 | 无默认访问权 |
| 创建交办、确认决定与完成 | 按老板明确指令及有效内容版本执行 | 无业务决定权 |
| 修改目标、私人设置和个人记忆 | 本人查看、确认、修改、删除 | 维护功能，不能自行改变本人要求 |
| 配置模型、工具及调度 | 查看启用能力及相关费用，管理本人计划 | 维护运行参数、连接、暂停与故障检查 |
| 管理演示材料与指标 | 查看来源、公式、版本和范围 | 配置模拟数据、公式、场景、回复和专业结果 |
| 检查确认记录 | 查看本人动作及其实际结果 | 按授权检查记录，无权替代本人确认 |

权限由服务端检查请求身份、老板授权和对象范围。模拟联系人 ID 只标识资料与消息对象，不能用作登录凭据。未认证请求、维护身份越权、工具超出老板授权均需要明确拒绝。

### 11.5 动作确认与使用负担

读取获准资料、执行查询、生成草稿和整理会前材料可以在交办范围内持续完成。发送消息、修改日程、提交决定和确认完成，根据动作类型及已有授权检查。

如果用户已经明确指定对象、内容和动作，并且内容版本及授权仍有效，应记录该授权并执行。只有收件人、正文、金额、时间或授权范围等决定性条件缺少或发生变化时，才提出具体确认问题。

动作页面显示将要处理的对象、内容、范围和当前状态。用户取消操作后，系统停止尚未执行的动作；已经完成的动作如实保留，需要新的变更操作才能改变结果。

### 11.6 后台与开源能力的复用职责

| 能力组 | 可复用的内容 | 本产品负责的内容 | 需要保持一致的状态 |
|---|---|---|---|
| 会话与模型运行 | 所选项目的运行服务、模型适配和事件输出 | 老板身份、任务关联、配置生效与结果展示 | 当前会话、运行标识和模型配置版本 |
| Skills 与任务方法 | 所选项目支持的 Skills、Tools 和 MCP 扩展 | 秘书 SOP、BI 工具、确认规则和业务检查 | 启用能力、版本和工具范围 |
| 记忆与资料 | 文件处理、检索和记忆基础能力 | 来源属性、个人确认、访问范围、资料有效版本 | 当前有效记忆与检索结果 |
| 定时与事件 | 所选项目已验证的调度机制 | 经营触发规则、通知对象、重复控制和模拟时钟 | 唯一有效计划与执行状态 |
| 运行管理 | 所选项目提供的日志、用量和管理接口 | 业务结果、数据集关联、错误说明和演示检查 | 配置、工具调用与业务结果可以相互查询 |
| 模拟业务与老板页面 | 成熟的界面、存储、解析及 API 库 | 统一模拟环境、经营对象、个人工作页面和业务权限 | 页面、接口与任务查询使用相同状态 |

后台的管理区域表示所需能力，不规定每项能力对应一个独立页面或独立服务。已有管理功能可以直接复用或通过正式接口接入；每项能力都需要说明实际维护位置和操作结果。

## 12. DeepSeek 模型配置

### 12.1 已确认的模型计划

| 配置 | 用途 | 需要形成的证据 |
|---|---|---|
| DeepSeek 配置 | 完成聊天、工具调用、SOP、记忆与页面演示；从相同初始资料执行两次独立检查 | 实际 DeepSeek 请求、对应工具结果、用量和耗时 |

用户确认只使用 DeepSeek，API 密钥后续提供。具体型号通过服务端配置与后台管理，不能将模型标识写入业务页面或业务规则。

截至本次调查，DeepSeek 官方入门文档列出 `deepseek-flash` 与 `deepseek-v4-pro`，并说明 `deepseek-flash` 当前由 DeepSeek-V4.1-Flash-1017 提供服务。OpenAI 兼容入口为 `https://api.deepseek.com`，另提供 Anthropic 兼容入口。实施时应重新核查所选模型的可用性和参数。[DeepSeek API 入门](https://api-docs.deepseek.com/)

### 12.2 模型配置需要包含的输入

| 配置内容 | 需要明确的事项 |
|---|---|
| Provider 与配置名称 | DeepSeek 配置及显示名称 |
| API 类型 | Responses、Chat Completions 或其他所选 Provider 支持的协议 |
| 地址与模型 | `base_url`、`model_id`、所用版本信息 |
| 凭据 | 服务端凭据引用、连接状态；页面与普通日志不展示密钥 |
| 能力 | Tool Calling、Streaming、结构化输出、输入模态和上下文范围 |
| 推理参数 | 按模型支持的方式设置思考参数、输出限制和采样参数 |
| 运行限制 | 单次耗时、最大工具轮数、上下文预算、取消与超时行为 |
| 用量与费用 | 请求用量、缓存用量、计价日期、币种、费用是否为估算 |
| 生效信息 | 配置版本、启用时间、运行中任务与新任务的配置归属 |

模型接入需要记录所选 DeepSeek 型号对应的实际 API 类型，配置声明与请求路径分别保留证据。

DeepSeek Tool Calls 文档说明模型返回工具调用请求，由应用执行工具并传回结果；不同 API 格式的支持范围有差异，`strict` 模式另有 Beta 入口及 JSON Schema 限制。适配需要检查工具定义、历史消息、流式事件、推理参数和结果解析。[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)

### 12.3 模型切换与可检查性

- 后台切换模型时保存具体配置，下一次任务显示实际使用的 Provider、模型和 API 类型。
- 同一份业务工具定义可以通过对应适配连接不同模型，业务权限和数据状态保持一致。
- 使用相同初始数据集执行两次独立检查，每次拥有独立会话和业务写入空间。
- 配置不兼容、密钥无效、额度不足或调用失败时明确显示失败，不自动换成另一模型或预设回答。
- DeepSeek 的每次实际执行分别记录。没有实际调用的配置保持未验证。
- 运行记录显示模型返回的实际用量；缺少用量字段时标记未知，不能补成零。
- 成本展示区分模型费用、Embedding、语音和其他服务费用；没有完整计价信息时标注估算范围。

### 12.4 知识检索与语音服务

LLM、Embedding、Reranker 和语音转写是不同服务能力。使用 DeepSeek 聊天 API 不自动意味着已经具备文档 Embedding 或语音转写。

如知识检索需要 Embedding，可以使用成熟的本地模型或正式服务，后台记录模型、索引版本和连接状态。文档解析使用成熟库，实际执行摄取、检索和引用定位。语音入口使用真实转写能力，转写内容经过用户检查后进入任务。

本轮无需申请企业内网权限；应用运行所需的模型 API 凭据、网络访问与运行环境在建设时配置。

### 12.5 DeepSeek 共同检查任务

DeepSeek 的兼容性属于开源选型证据，需要在确定业务页面的接入方式前完成实际验证。

共同检查任务采用“查询经营指标、继续读取依据、保存一项已授权交办、重新查询结果”。两次独立执行均记录工具参数、执行结果、上下文续接、费用和耗时。模型生成的措辞可以不同，事实、授权和最终业务状态使用相同检查方式。

若目标模型失败，需要明确属于模型回答、API 适配、工具参数、业务接口或运行配置中的哪一项。错误结果保留对应记录，不使用另一个模型的结果标记目标模型通过。

## 13. 面试 Demo 的演示输入

### 13.1 连续演示过程

建议以一个模拟工作日串联业务，完整主流程约 8—12 分钟。时间是演示组织建议，具体运行耗时需要实际测量。

| 环节 | 演示者操作 | 系统需要实际完成的事情 | 可查看的结果 |
|---|---|---|---|
| 生成环境 | 在后台选择数据配置并生成场景 | 保存关联业务数据，显示数据集版本和模拟时间 | 接口目录、数据数量、生成结果 |
| 晨间安排 | 老板询问今天需要关注的事项 | 查询日程、任务、经营信息，组织个人简报 | 会议、异常、待决定与承诺清单 |
| BI 追问 | 询问销量增长与毛利变化 | 选择指标工具、查询明细、执行计算、引用口径 | 数字、维度、解释和未知部分 |
| 主动提醒 | 在后台触发一个经营事件 | 获取事件、执行规则、生成提醒并合并重复信息 | 老板通知、后台规则与调用记录 |
| 会前准备 | 要求准备与负责人的会议 | 关联历史承诺、事件、最新汇报和日程 | 会前材料、议题与待回答问题 |
| 交办与回复 | 确认一项交办，随后触发模拟回复 | 保存任务、模拟发送、读取回复并更新进展 | 任务详情、发件箱、回复和完成证据 |
| 记忆与配置 | 修改简报格式或提醒规则，再发起新任务 | 保存当前设置，并在新运行中使用 | 配置版本与行为变化 |
| 错误与模型 | 演示一个接口错误；使用 DeepSeek 执行两次独立任务 | 明确失败状态，分别保存模型运行记录 | 工具错误、DeepSeek 实际结果和用量 |

这些环节可以通过不同问法运行。演示脚本只帮助讲解，系统需要根据当次输入和状态执行。

### 13.2 一组可以复算的 BI 演示数据

以下全部为 `SIMULATED`，只用于数据生成与计算检查，与海大公开财务数据没有对应关系。演示对象设为一个合成区域的水产饲料外销业务，两个期间采用相同长度和业务范围，产品明细关联第 10.6 节的客户、工厂与养殖服务资料。

| 指标 | 基准期间 | 当前可比期间 |
|---|---:|---:|
| 销售数量 | 10,000 吨 | 12,000 吨 |
| 销售收入 | 4,000 万元 | 4,800 万元 |
| 销售成本 | 3,600 万元 | 4,416 万元 |
| 毛利 | 400 万元 | 384 万元 |
| 毛利率 | 10.00% | 8.00% |
| 单吨毛利 | 400 元 / 吨 | 320 元 / 吨 |

这组数据支持确认：销量和收入均增长 20%，毛利减少 4%，毛利率下降 2 个百分点，单吨毛利减少 20%。数据生成器需要生成能够汇总到这些数值的明细。

“价格、原料成本或产品结构分别贡献多少”需要相应明细才能回答。演示数据可以配置产品或区域贡献；没有配置相应资料时，Agent 应说明仍需哪些信息。

### 13.3 可扩展演示主题

除连续主流程外，场景库保留审批材料不足、行程冲突、私人资料权限、公开报告阅读、资料更新、任务取消和模型错误等主题。它们共用数据、接口与运行管理机制，可以单独触发检查。

私人安排、人员会面和重要客户接待使用合成身份与材料。对外发送、日程变更和审批均通过模拟接口实际更新相应状态。

### 13.4 老板如何处理一项毛利变化

以下推演使用第 13.2 节的合成数字，联系人、会议、反馈和业务时间均属于演示数据。老板操作个人入口，技术维护者从模拟中心提供事件和材料，模型根据当次材料回答。

| 顺序 | 参与角色与交办 | Agent 与工具需要完成的工作 | 留下的可查询结果 |
|---|---|---|---|
| 01 | 维护人员载入数据，推进到晨间汇总时间 | 获取销售与财务数据，检查范围和更新时间 | 数据集、接口调用和有效资料版本 |
| 02 | 老板查看今天的经营关注 | 说明销量增长 20%、毛利减少 4%、毛利率下降 2 个百分点，并关联增长质量目标 | 有公式和来源的关注内容；提醒规则及触发依据 |
| 03 | 模拟接口提供财务核查说明 | 关联核查意见，明确哪些原因尚无足够明细支持 | 财务说明及对应版本；已知事实与待核查内容 |
| 04 | 老板要求 Agent 准备经营会议 | 查找上次相关承诺、当前负责人和材料，整理议题及缺少资料 | 会前材料、联系人和准备事项 |
| 05 | 老板追问产品结构的影响 | 查询可用明细；缺少数据时说明所需资料，不能按场景名称生成原因 | 查询记录、明细依据或明确的资料请求 |
| 06 | 老板交办负责人提交解释与措施 | 保存任务目的、责任人、期限和所需证据，按已有明确授权模拟发送 | 任务记录、模拟发件箱和当前授权 |
| 07 | 模拟接口返回负责人措施或延期申请 | 关联原任务，区分业务判断、完成证据和待决定申请 | 反馈记录、原期限及变更申请 |
| 08 | 老板查看反馈与模拟财务核查材料 | 对照原交办检查证据，呈现未解释内容及可发送的补充请求 | 核查摘要、补充草稿和有效材料 |
| 09 | 老板确认任务完成 | 保存本人授权与结果，更新后续提醒；指标状态继续按实际数据判断 | 已确认任务及依据，仍有效的经营关注 |
| 10 | 老板修改以后关注此类事件的要求 | 保存经本人确认的新设置，在下一次事件中采用 | 个人设置版本和新运行结果 |

解释任务完成不表示毛利指标已经恢复。业务问题、核查任务和提醒分别维护当前状态，并通过关联标识连接。

| 人员相关会面 | 组织负责人目标、历史交办和反馈 | 工作事实、沟通问题及获准资料 | 复用会前能力，使用合成人员和任务关系 |
| 出行与接待 | 修改行程并查看会议和准备事项的变化 | 时区、冲突、受影响安排与修改记录 | 复用日期及资料工具，建设模拟行程接口 |
| 私人安排 | 老板查看私人时间与工作冲突，并检查维护身份访问限制 | 本人查看正文，分享内容按授权控制 | 复用日历能力，建设对象范围检查 |
| 长期决定与学习 | 新会话查询历史决定并修改个人要求 | 历史依据、有效记忆和新任务采用结果 | 复用记忆基础，建设确认、版本和引用关系 |

模型配置、模拟环境、后台操作、错误处理和评测属于这些任务的共同支撑。交付完成不依赖为每个主题建设独立业务系统，也不依赖为每个管理区域建设独立页面。

### 13.6 面试官可以现场改变的内容

演示者可以提供新的提问方式、不同的查询期间、一个同名联系人、一份有冲突的汇报，或者在任务中途改变交办条件。应用需要依据新的输入和当前状态继续工作。

面试讲解需要能够回答：为什么该事项需要老板关注、哪些判断来自规则、哪些工作由模型完成、数据如何取得、动作是否执行、错误在哪里，以及本人具体完成了什么。每项回答都对应可打开的材料或实际运行记录。

### 13.7 农业经营专题与可执行的秘书任务

下表全部属于演示设计，业务事件与数字由模拟接口产生。每项专题复用老板的查询、会议、交办和跟进功能；专业结果由对应角色提供，模型根据当前材料组织解释。

| 专题与老板提问 | 后台提供的事件及材料 | Agent 需要完成的工作 | 需要老板处理的事项 | 可以检查的结果 |
|---|---|---|---|---|
| 原料与饲料：“报价上涨，哪些产品何时受到影响？” | 报价变化、采购合同、库存批次、配方版本、生产计划与成本 | 区分行情与实际成本，查询有效批次，按给定假设测算并列出未知条件 | 采购、产品与工厂之间的资源协调申请 | 可复算影响、条件说明、会议材料及交办状态 |
| 水产季节：“这个区域订单减少，需要关注什么？” | 同品种历史周期、天气、投苗投喂记录、渠道库存、订单和技服反馈 | 检查季节和数据覆盖，分别列出需求事实、客户反馈及待验证原因 | 区域提出的供应调整或服务资源请求 | 比较范围、证据、统筹负责人和复查安排 |
| 苗种批次：“几位养户的反馈是否涉及同一批次？” | 养户反馈、苗种交付、运输、接收、放养条件与回访 | 查询共同批次及不同条件，显示受访范围，汇总需专业确认的问题 | 跨区域联合核查或客户服务协调 | 追溯关系、覆盖说明、专业反馈和处理进展 |
| 动保与技服：“这个健康问题谁在处理，结果是否确认？” | 观察、采样检测、专业意见、措施与后续观察时间 | 区分报告、专业确认、执行及复查状态，识别缺少材料或专家资源 | 多地共享专家与服务资源的协调 | 专业责任、证据和下一次复查时间，不直接生成用药指令 |
| 生猪合作：“这批出栏结果为什么变化？” | 仔猪与投入品成本、饲养记录、转群、出栏价格、合作费用及结算 | 核对同一批次与成本归属，分别展示生产表现、价格影响和未结算项目 | 经营复查、合作问题或资源申请 | 可复算的周期结果、费用归属和负责人解释 |
| 禽类与反刍：“销量变化集中在哪种动物和生产阶段？” | 肉禽、蛋禽或牛羊客户记录，阶段供料、产出与服务资料 | 使用相应单位和指标，查询客户需求与饲喂结果，提出核查问题 | 产品服务安排与区域资源协调 | 正确的动物、用途、阶段和统计范围 |
| 公司水产养殖：“这项设备或环境事件影响哪些批次？” | 自营养殖单元、设备与巡检、观察时间、批次、计划和处理记录 | 关联受影响单元与当前措施，区分观察事实、估计影响和已确认结果 | 跨单位设备、人员或供给资源申请 | 有时间依据的事件材料、已授权交办与专业复查 |
| 食品与品质：“这项客诉涉及哪些库存和客户？” | 客诉、原料及加工批次、检验、库存、交付与专业处置意见 | 查询已确认关联，列出追溯缺口与待处置事项 | 重要事件的统筹协调与后续检查 | 关联清单、专业结论、任务进展和状态变更 |
| 海外业务：“增长很好，交付和资金是否跟得上？” | 本地订单、工段能力、排产、物流、回款、币种与时区 | 分析供需及交付缺口，按可比口径呈现经营数据，准备跨时区会议 | 产能、人员、供应或资金安排的正式申请 | 国别资料、量化依据、选项与决定期限 |
| 研发应用：“这个产品效果能支持下一项推广决定吗？” | 试验条件、对照数据、专业评审、应用范围及客户反馈 | 整理证据、限制条件与尚未验证的场景，关联原目标和资源申请 | 是否要求继续验证、调整项目或采纳已评审安排 | 有范围的效果解释、专业评审和老板决定记录 |

同一区域同时出现订单减少、天气变化和健康反馈时，Agent 不能仅凭时间接近认定原因。需要检查品种、地域、养殖批次、观察日期、覆盖范围与专业核查结果；有多种合理解释时，保留证据支持程度与待确认问题。

### 13.8 将农业流程连接到连续面试演示

主流程使用第 13.2 节的水产饲料毛利数据，以及同一合成区域的客户服务、采购、工厂和回款资料。公开年报只作为背景知识，不参与合成金额的明细计算。

1. 老板在晨间询问“今天哪些经营事项需要我处理”，系统发现水产饲料毛利变化，并关联当日经营会议和未完成交办。
2. 老板继续询问“涉及哪个品种、哪些客户和工厂”，系统按当前可用明细查询，同时显示未同步的养户观察范围。
3. 老板追问“养户这个周期的经营情况怎样”，系统关联同一客户的养殖批次、投入、起捕或预计销售及技服资料，分别表达客户结果与公司经营结果。
4. 后台触发一项原料到货变化。系统根据当前库存、质量状态、有效配方和订单判断是否存在具体供给缺口；缺少条件时提出核查要求。
5. 老板 Agent 生成经营会议材料，关联模拟接口提供的产品、区域、采购、工厂和财务说明。会议材料展示已有共识、资料冲突、统筹负责人和需要老板决定的事项。
6. 老板确认一项跨职责协调交办。系统实际保存任务并模拟发送，记录所需材料、期限、关联经营事件和负责人。
7. 模拟中心提供业务回复及财务核查。系统比较承诺与证据，提示尚需专业确认或继续观察的内容；老板确认完成后更新本人交办状态，专业结果继续作为来源资料保存。
8. 推进到下一次复查时间。系统读取新数据，分别说明经营指标是否变化、交办是否完成、客户周期是否已经结算，以及老板是否仍有待处理事项。

演示者可以选择第 13.7 节中的其他业务专题继续追问。系统共用相同的人员、事项、资料和运行机制，并依据所选业务使用对应指标与专业责任。

## 14. Demo 完成的检查方向

验收中心是应用可以启动并完成演示。每个核心任务需要能够从用户输入到最终结果实际运行，操作结果可以重新查询。真实企业试用、内部系统连接和业务收益证明不作为此次完成条件。

| 检查内容 | 检查材料 | Demo 达到的结果 |
|---|---|---|
| 应用启动 | 启动记录、服务状态、老板页面、后台页面 | 页面和服务可访问，连接状态明确 |
| 模拟环境 | 生成参数、数据集版本、接口调用 | 生成的业务材料能够被工具实际读取 |
| 真实模型调用 | Provider、模型、请求标识、用量、工具调用 | DeepSeek 完成演示与两次独立共同任务，分别有实际结果 |
| BI 正确性 | 明细、公式、范围、单位和数据时间 | 数值可复算，来源与模拟属性明确 |
| 个人秘书任务 | 日程、材料、会议、联系人和任务 | 结果与当前工作上下文一致，能够继续追问 |
| 动作与状态 | 模拟发件箱、审批、任务和更新记录 | 确认后的动作实际更新数据，可重新读取 |
| 主动工作 | 实际调度记录、事件、规则和通知 | 时间或事件能够触发运行，暂停与取消有效 |
| 记忆更新 | 保存内容、版本、新会话结果 | 当前有效要求被使用，删除内容不再被检索采用 |
| 后台配置 | 保存记录、页面重载、下一次运行 | 保存与生效一致，未启用能力有明确状态 |
| 错误场景 | 不可用、过期、不完整、权限与重复请求 | 如实表达问题，业务结果不被误标成功 |
| 费用和速度 | 实际 Token、耗时、计价配置 | 可以说明单次任务用量与耗时，未知数据明确标注 |
| 可重复演示 | 重置、相同初始数据、独立运行记录 | 关键事实与动作检查仍成立，历史结果不会混入 |

验收记录使用场景、初始数据、操作、预期检查、实际结果和运行链接。完成状态依据实际记录填写。演示完成率按预设任务集计算，不能替代业务收益或生产可靠性指标。

功能实现期间需要运行实际服务和页面，执行核心演示及必要的异常检查，修正问题后再次验证。不能将应用交付后的首次完整检查留给用户承担。

### 14.1 老板任务的检查维度

| 检查视角 | 需要确认的结果 | 明确不能通过的情况 |
|---|---|---|
| 老板 | 关注内容与目标和本人责任有关，可以继续追问并采取动作 | 重要事项遗漏，普通变化反复打扰，无法说明需要本人处理的原因 |
| 秘书工作完整性 | 材料、人员、日程、决定和交办可以相互查询 | 使用错误联系人，遗漏准备材料，日程已变更但准备清单未更新 |
| 老板交办有效性 | 任务目的、责任人、期限和所需证据清楚 | 没有老板授权就改变期限，将收到回复直接标记为完成 |
| 经营解释准确性 | 公式、范围、期间、单位和资料版本一致 | 使用不匹配口径计算，凭空解释原因，把未同步范围记为零 |
| 资料来源有效性 | 数据属性、更新时间、有效版本和范围可检查 | 合成数据被标成海大内部事实，引用已撤销资料却没有说明 |
| 技术与维护人员 | 配置生效、运行可查、写入状态正确、目标模型实际执行 | 后台显示与运行不一致，重复写入，模型失败后伪报业务成功 |
| 评测人员 | 相同检查能够覆盖不同问法与未知组合 | 根据场景标签输出答案，只靠模型自评判定动作完成 |
| 面试官 | 能够检查业务判断、个人贡献和技术实现之间的对应关系 | 演示无法接受合理追问，无法说明复用范围或提供实际结果 |

### 14.2 检查结果如何记录

每项结果记录输入、数据集、角色、授权、模型配置、关键检查、实际输出和业务状态。数值正确性采用原始精度与明确的展示舍入规则；状态检查以重新查询业务记录为依据。

固定演示任务和未预先编排的变体分别记录。数值错误、无授权操作、重复业务写入、合成数据来源标记错误和错误的完成状态均需要修正并重新验证，不能由平均得分抵消。

用量、等待时间、人工核查时间和修改量分别测量。尚未给出费用与时间上限时，不填入臆测的通过数值；演示前根据实际运行记录确认可接受的费用和节奏。

### 14.3 农业经营场景的检查

本节检查模拟环境中的业务表达、数据关系和秘书动作，不要求取得真实养殖试验结果或企业经营收益。

| 检查内容 | 演示中的检查方法 | 达到的结果 |
|---|---|---|
| 产品与区域协作 | 同一事项分别按产品、区域和法人查询 | 指向相同业务记录，汇总数量没有重复累计 |
| 客户与公司关系 | 同时查询客户养殖、合作农场和公司养殖 | 资产、成本、利润与应收归属明确 |
| 内部供给 | 同时提供内部耗用和对外销售记录 | 数量能够分项显示，合并收入采用已配置的财务口径 |
| 生物与时间范围 | 更换品种、阶段、批次、季节或比较期间 | 使用适用指标和可比范围；条件不足时说明限制 |
| 估计与覆盖 | 提供局部回访、旧观察和存塘估计 | 明确观察日期、覆盖与估计方法，不生成全量确定结论 |
| 批次追溯 | 提供共同批次、相似名称和缺少关联的多组记录 | 只按已有关系追溯，缺少关系继续保持待核查 |
| 因果解释 | 同时出现行情、天气、产品和客户变化 | 区分事实、假设和专业确认，不把共同出现当作因果证据 |
| 生产与质量 | 库存包含待检或限制使用批次 | 可用供应计算遵守当前质量状态与适用条件 |
| 数值复算 | 改变一个批次数量、成本或价格 | 明细、汇总和影响测算随有效数据更新 |
| 专业职责 | 提供观察记录但缺少专业确认 | 保留待核查状态，建立获准任务，不自行发布专业处置指令 |
| 老板参与条件 | 同一事件分别配置负责人可处理与需跨职责协调 | 提醒内容及对象符合当前授权，能够解释老板参与原因 |
| 周期与任务状态 | 提交服务回复，但养殖周期尚未结束 | 服务任务、业务事件与养殖结果分别更新，保留复查安排 |
| 海外经营 | 改变币种、汇率日期或本地时区 | 可比金额、日期、会议时间和资料范围保持一致 |

第 13.7 节每个专题都需要保留一次完整运行记录，并覆盖与该专题有关的数据缺少或状态变化检查。后续建设验收引用本节，不将研究假设写成已经验证的生产能力。
