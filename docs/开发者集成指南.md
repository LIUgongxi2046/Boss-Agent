## 2. 认证与传输

产品模式由 `BOSS_PRODUCT_UI=1` 启用。`GET /webui/bootstrap` 同时接收 `X-Boss-Username`、`X-Boss-Password`、`X-Boss-Role`，或者使用有效 `Authorization: Bearer <api_token>` 刷新。身份取自账号数据库，合法角色为 `BOSS`、`MAINTAINER`。请求不能携带查询参数；提供 Origin 时，必须与 Host 的地址一致。

账号名限 ASCII、长度1—64；密码限 ASCII、长度1—72。密码通过 bcrypt 校验。`accounts.sqlite` 与 `credentials.json` 权限为0600，目录为0700；凭据不进入项目文档、URL或普通日志。

成功响应含 `token`、`api_token`、`ws_path`、`ws_url`、`expires_in`、消息及附件限制、模型名、当前宿主能力，并设置 `Cache-Control: no-store`。令牌有效期读取 `expires_in`，应用初始配置为3600秒；已有实例采用其实际配置。业务 HTTP 使用 `api_token`，原生 WebSocket 使用 bootstrap 返回的连接信息。这里没有 JWT 格式或独立 refresh token 的约定。

`GET /api/boss/identity` 返回 `role`、`owner_id`、`execution_scope`、`execution_namespace`。BOSS 的 `owner_id` 为 `boss-1`；MAINTAINER 的 `owner_id` 为 null。未配置 `BOSS_EXECUTION_SCOPE` 时 `execution_scope` 为 null。客户端不能通过 payload 或 URL 更改业务主体及执行空间。

| 通道 | 请求与结果 |
|---|---|
| HTTP 读取 | `/api/boss/ui/*`，Bearer 认证；实际公开入口为 WebUI 端口 |
| WebSocket 业务操作 | `type=webui_request`、`request_id`、`action`、`payload`；响应采用 `event=webui_response`、相同 `request_id`、`ok`、`result` 或 `error` |
| 原生聊天与流式回答 | 复用 nanobot 会话和 WebSocket 事件；事件字段见 [runtime-events.schema.json](../specs/runtime-events.schema.json) |
| 原生会话取消 | 向当前会话提交 `/stop`，停止后续步骤；已经提交的业务结果继续查询 |
| 主动退出 | `boss.auth.logout` 撤销当前角色的令牌及关联连接，保留业务记录 |

当前业务流式传输采用 WebSocket。SSE、`Last-Event-ID`、第三方 Webhook 订阅与签名回调没有本次核查范围内的实现，调用方应使用原生事件及正式回执读取。HTTP 错误可能是认证文本，也可能是 JSON 业务错误，客户端需结合状态码与 Content-Type 处理。

## 3. 经营范围与模型分析

1. 调用 `GET /api/boss/ui/business-overview/dimensions` 或 `boss.business_overview.dimensions`，读取当前合法法人、区域、期间和时区。HTTP 入口不接受查询参数，WebSocket payload 为 `{}`。
2. 调用 `boss.business_overview.read`，提交完整 `Scope`：`legal_entity_id`、`region_id`、`period_start`、`period_end`、`timezone`、`attention`。`region_id=null` 表示没有区域限制，`attention` 为 `ALL`、`OWNER_INVOLVEMENT` 或 `SOURCE_REVIEW`。期间必须完整匹配当前目录提供的范围。
3. 保存返回的 `applied_scope`、`snapshot_sha256`、来源及资料缺口。选择专题时通过 `boss.business_overview.detail` 传入 `scope`、`page_id`、`snapshot_sha256`；禽畜 `F19` 可增加 `use`，取值为 null、`BROILER`、`EGG`、`MILK`、`BEEF`。
4. 进入分析前，通过 `boss.conversation.business.prepare` 提交 `client_request_id`、`applied_scope`、`snapshot_sha256`、`topic_reference`。创建并订阅真实原生会话后，以 `boss.conversation.business.bind` 提交同一编号、`preparation_id`、`preparation_sha256`、`chat_id`。
5. `boss.conversation.business.read` 使用 `chat_id`，可增加布尔型 `adopt_selection`；当前连接必须订阅相应会话。服务端重新核查绑定、来源和版本，随后通过原生会话提交问题。`BusinessConversationEntry` 在绑定成功后提交分析问题。
6. 模型工具 `businessOverviewRead` 的唯一参数为 `{"projection":"current"}`，返回服务端绑定的总览或专题。经营会话工具范围为 `businessOverviewRead`、`query_metrics`、`bossEvidenceRead`。参数范围和数据来源由服务端确定。

`BusinessOverviewAPI.topic_in_transaction` 为经营详情、会议准备和经营工具共用的专题读取。蛋禽、奶畜、肉用牛羊各自采用对应数值、单位与来源；来源变化参与快照摘要。`query_metrics` 的可用范围仍取决于当前 `query_handoff`，不能据十类专题目录推断全部专题具有相同计算口径。

`GET /api/boss/ui/sector?page=<page_id>` 用于专题工作区；可选 `filters` 为 JSON 字符串形式的字符串键值对象，合法筛选名称来自该页面设计配置；可选 `overview_reference` 为 JSON 对象。支持十类主专题及 `V19-EGG`、`V19-MILK`、`V19-BEEF`。未知页面返回404，不支持的筛选返回400；全部专题业务验收继续保留原检查要求。

## 4. 保存、恢复与错误处理

传输层 `request_id` 与业务 `client_request_id` 分别使用。后者的格式采用具体动作 Schema；经营入口为8—128位 ASCII 字母、数字、下划线、句点或连字符。对同一次业务意图始终保留原编号；相同编号、相同内容读取原结果，相同编号、不同内容被拒绝。

经营准备回执通过 `GET /api/boss/ui/conversation/business-entry?client_request_id=<原编号>` 或 `boss.conversation.business.receipt` 读取。结果为 `RECORDED` 或 `NOT_FOUND_IN_CURRENT_STORE`，历史回执的 `current_use_verified=false`；继续进入需要重新核查准备与绑定。`boss.conversation.business.clear` 使用空对象，清理当前连接的经营选择，不删除历史业务记录。

| 状态或结果 | 集成处理 |
|---|---|
| 400 | 核查字段、类型、完整期间及合法筛选；保持用户输入和原编号 |
| 401 | 当前认证无效，通过产品登录恢复身份 |
| 403 | 核查当前角色、来源权限及会话订阅；不能由客户端改写身份 |
| 404 | 当前存储中没有所请求对象；核查实例、对象编号及原回执 |
| 409 | 对象、来源、范围或执行空间发生变化；读取当前资料并按正式流程重新确认 |
| 410 | 对应来源已经撤销或过期，停止继续采用 |
| 503 | 所需 Runtime、方法或领域服务未准备，修复服务条件后查询原编号 |
| 请求中断或状态未知 | 读取原回执和业务对象；不自动重放写入或发送 |

本人授权、CAS、来源摘要与幂等核查在正式服务端执行。模型回答、页面读取和准备结果均不能签发本人决定；交办、发送、延期、完成和审批分别使用正式动作及当前版本。
