## 1. 产品判断：从“页面集合”走向“可执行的老板智能助手”

**建议的产品定位**：老板用一句话提出经营或管理问题，大鹏能够理解意图、在获准范围内查找证据、调用工具、提出可解释建议，必要时形成交办或申请，并在老板明确授权后执行、持续跟踪到结果核查。

老板希望完成的不是“查一个指标”“打开一个页面”，而是：

1. 今天哪些事情必须由我处理？为什么排在前面？
2. 毛利为什么下降？数据依据在哪里？是否需要调查？
3. 我刚才说的事情交给谁了？是否真正创建或发出？
4. 上次会议定下来的事情进展怎样？为什么还没完成？
5. AI 是否越过我的授权、引用过期信息或编造执行状态？

管理员希望完成的是：

1. 当前 Agent 具备哪些技能、工具和数据访问权限？
2. 模型、Prompt、SOP、知识库、接口究竟哪一层没工作？
3. 这个配置是否已被实际 Run 采用，而不只是保存成功？
4. 如何重放／排查一次失败，恢复但不重复执行？
5. 如何用独立评测验证修改后没有出现权限、计算或工具错误？

### 1.1 当前最高风险

N02 是产品价值中枢。最新界面调整不能代替真实 Agent 能力：需要验证从自然语言输入、模型选择工具、服务端权限核查、读取企业数据、组织结论、生成任务草稿、老板授权、业务写入、原回执恢复，到其他页面能读到同一业务状态的全链路。

现有页面的独立功能应优先复用，不建议为了“更像 Agent”引入第二套会话／任务状态或重写上游 nanobot。真正需要的是把当前 Runtime、Tool Registry、领域 API、原生 ClientProvider 和 Boss 业务页面连通，并使实际结果在界面可见且可追溯。

### 1.2 建议的产品信息架构

老板常用顶层入口保留六组：今日工作、聊天交办、经营关注、会议与资料、任务与承诺、通知与设置。F14—F23 等专题页面保留，通过搜索、经营卡片和聊天产物深链进入；不要求老板每天在 30 多个页面中查找信息。

管理员按模拟与数据、档案与访问、Agent 配置、运行与评测四组维护。配置、校验、启用、真实运行采用、回滚是不同状态。管理员不能以模拟用户、技术身份代替老板作商业决策。

## 2. N02 聊天交办：第一优先级专项改造

### 2.1 真实用户故事 BA-CHAT-01

**作为老板**，我输入：“帮我看看本月原料成本上涨的情况，主要是什么原因。如果异常，整理要处理的事情，交给相关负责人，下周一之前反馈。”我期望得到一份有来源的分析和一个可由我确认的交办，而不是一段看起来聪明的泛泛文字。

**Given**：当前 BOSS 身份有效，已授权可访问必要经营数据，相关指标、期间、业务口径与联系人资料具有来源版本。  
**When**：老板发送自然语言请求并必要时补充产品／法人／期间。  
**Then**：

1. 正确识别“成本查询、比较、原因调查、拟定交办、期限解释”多个意图。
2. “本月”和“下周一”结合业务时区、请求日期解释；范围歧义时先询问。
3. 依据当前合法数据调用经营工具，原始值、公式、比较条件、缺口与时间版本可重查；无证据时不编造原因。
4. 在界面展示已做步骤、下一步、查得的资料和当前不确定性。
5. 形成交办草稿，列明目的、唯一负责人候选、交付物、期限／时区、依据和待确认字段。
6. 没有老板明确授权时，不创建已发送的任务，也不替老板签发同意。
7. 老板修改／确认后产生一次带 ID、版本、幂等回执的业务结果；模拟通道必须标识 SIMULATED。
8. N05 与 F06 读取同一任务；后续问“那件事怎么样了”能够定位原任务状态和反馈，不重新发明任务。
9. 模型超时、网络中断或响应丢失时，根据原请求编号查状态，不发起重复的写入。
10. 老板可随时打开 D01 原始证据、D02 必要决定及 D03 结果核查。

### 2.3 页面交互的必要调整

- **左侧**：会话搜索、新建、历史会话、任务关联；所有会话操作与当前身份同源。
- **主对话区**：保留成熟流式消息、Markdown、表格和附件；在回复中内嵌“数据查询／工具调用／执行进度／授权卡片／执行结果”，不把技术轨迹伪装成答案。
- **右侧上下文区**：当前任务目标、关键业务对象、待确认动作、资料版本、已生成产物；普通闲聊允许收起，避免三栏长期挤压阅读。
- **直接业务入口**：可从经营结果“继续让大鹏分析”，从任务详情“继续讨论”，从会议资料“整理会议议题”；进入 N02 时附带稳定对象 ID 与可验证的上下文。
- **状态与信任**：明确区分模型正在生成、工具运行中、等待老板授权、业务确认完成、发送待送达、模拟执行、结果未知及运行失败。

### 2.4 关键技术接入建议

建议复用现有 nanobot AgentLoop、SessionManager、WebSocket、ClientProvider、Tool Registry、RoleChannel 和 SQLite 业务服务：

老板输入 → 可信身份／会话上下文 → AgentLoop 规划与工具选择 → 服务端工具白名单及对象权限核查 → 领域服务读取／预检 → 有来源的分析／草稿 → 老板独立确认 → 幂等业务写入 → 回执与事件持久化 → N05/F06 等页面读取同一对象。

优先核对六个具体断点（均先标 CHECK，确认后才登记缺陷）：

1. 业务页面有读取接口，但运行时 Tool Registry 未注册或未采用。
2. 工具调用有记录，但对话区只展示自然语言，没有真实输入输出与产物映射。
3. 当前对象、期间、来源版本、角色范围在多轮对话中丢失或混用。
4. 会话交办草稿与实际任务中心对象无法双向关联。
5. 运行成功只是模拟 Provider 生成的结果，缺少真实的业务副作用和回执。
6. 网络超时后自动重发写入、旧响应污染新会话或跨身份泄露业务正文。

当前项目明确采用 SIMULATED_FIRST，且没有新增真实外部调用的默认授权。需要真实 DeepSeek／外部系统联调时，应在项目允许的准确范围中单独执行；不能把外部模拟通过写成生产真实执行。

## 7. 跨页面用户故事：真正的产品验收主线

逐页检查主要查字段、布局、状态与局部操作；完整产品验收必须按用户故事连续执行。建议下列 14 个稳定故事作为后续实测任务库。

| 故事 ID | 用户目标（Given / When / Then 摘要） | 关键页面 | 关键可观察结果 | 优先级 |
| --- | --- | --- | --- | --- |
| US01 晨间重点 | 有任务与经营资料时，老板打开工作台并询问重点 | F01、N02、N05 | 排序有依据、可追问、同一任务可读 | P0 |
| US02 经营异常分析 | 老板问成本／毛利变化及原因 | N02、N03、F03、F14、D01 | 实际指标工具、口径、来源、未知与对比 | P0 |
| US03 任务交办 | 老板说“交给负责人下周反馈”并确认 | N02、D02、F06、N05、F08 | 唯一任务、授权、回执、反馈、状态机 | P0 |
| US04 会前会后 | 老板准备会议并确认纪要 | N04、F04、F05、F06 | 会议→资料→决定→交办版本一致 | P1 |
| US05 审批处理 | 老板核查一项带附件的申请 | F07、D02、N11 | 批准／拒绝／补资料分支和历史可追溯 | P1 |
| US06 计划提醒 | 老板设置周期性事项与通知限制 | N09、N06、A13、D09 | 授权触发、抑制、记录、停止 | P1 |
| US07 专题研究 | 老板委托调研并要求证据和方案 | F09、N02、D01 | 可检查来源、分析步骤与结论边界 | P1 |
| US08 记忆更正 | 老板要求记住／纠正目标偏好 | F13、N07、N02 | 确认、采用、失效、纠错并可核查 | P1 |
| US09 技能发布 | 管理员配置并测试一项采购技能 | A05—A09、A15、A16、N02 | 版本与真实运行一致、工具轨迹可查 | P0 |
| US10 资料维护 | 管理员更换一版数据与知识材料 | A01、A03、A07、A11 | 索引刷新、来源失效、受影响业务标记 | P1 |
| US11 失败恢复 | 写入后中断或超时 | N02、D03、F29、A15 | 原编号只读恢复、不重复写入 | P0 |
| US12 权限隔离 | 管理员试图读取／批准老板私有事项 | N01、D07、N10、A14 | 服务端拒绝、无敏感泄露、最小审计 | P0 |
| US13 本地恢复 | 关闭桌面并重启合法服务 | F32、N02、N05、A15 | 版本、对象、状态、幂等回执可恢复 | P0 |
| US14 专题业务 | 不同业务板块同样能查询与追问 | F15—F23、V19、N03、F03 | 正确业务数据与单位，不返回别的场景答案 | P2 |

### 7.1 US03 详细验收脚本

**前提**：独立测试数据与端口，已知 BOSS 身份，准备一名稳定联系人和一条合法来源；外部通信为显式模拟时不得描述为真实送达。

1. 从 N02 输入“请让采购负责人核查本月主要原料上涨原因，下周一反馈。”
2. Agent 解析目标与时间，查询／确认负责人；缺少唯一联系人或数据依据时提出待补充字段。
3. 界面显示任务草稿、当前来源、负责人和期限；此时 N05 不得有“已发送”假记录。
4. BOSS 在 D02 核查后确认；检查 request_id、task_id、状态、版本、审计，确认只发生一次合法创建／模拟发送。
5. 从 N05 和 F06 重读同一 task_id，负责人、期限、来源与状态一致；返回 N02 继续讨论原任务。
6. 管理员通过获准模拟反馈入口提交“处理中”，仅更新反馈，不得代替老板确认完成。
7. 对任务催办、提出延期、提交结果并在 BOSS 核查后确认完成；分别检查状态和历史。
8. 制造连接中断、重复确认和旧来源版本；检查原编号恢复、旧版本冲突与零重复写入。
9. 切换到 MAINTAINER 身份访问私有授权详情，服务端拒绝且不泄露正文。
10. 重启独立候选并重新进入，原 task_id、反馈、决定、回执与会话关联仍在。

**通过定义**：上述合法主路径、失败分支、权限拒绝及持久恢复全部通过；任何未授权写入、重复写入、虚构送达、跨身份泄露属于 P0。

### 7.2 测试覆盖规范

每个用户故事必须记录：

- 准确 main 提交、工作树状态（若适用）、构建制品及实际运行版本。
- 操作系统、浏览器／Electron、视口、测试账号角色、隔离数据库和数据集版本。
- Given 前置数据、When 用户动作、Then 预期结果、实际结果和可重放步骤。
- UI 状态：加载、空数据、成功、失败、断线、权限、来源变化、取消、UNKNOWN、重启。
- 真实 Tool/Run/业务对象的 ID、来源版本、时间及结果关联；不记录 API Key、密码或受限业务正文。
- 判定：PASS、FAIL、BLOCKED、NOT_RUN；对 BLOCKED 写明缺少的具体依赖。
- 修复归属与复验依据；历史测试的适用提交不能自动搬到新候选。

产品安全门槛：业务本人授权严重错误为 0，伪造已执行动作 0，重复业务写入 0，来源不正确却宣称确定分析 0。这些是目标，不是当前测量值。

## 8. 跨角色共性问题与设计指导

### 8.1 页面联通

从任意经营图表点击“继续分析”，要携带当前对象、时间、法人／地区、指标、查询 ID 与合法来源版本；从会议进入会话，要携带会议对象和适用的材料；从聊天查看任务后返回，要恢复历史会话而不重新执行动作。路由、History、刷新、客户端连接及不同页面之间不得出现第二份互不一致的业务状态。

### 8.2 用户能理解的 Agent 反馈

- **看得见步骤**：正在检索哪些合法资料、哪些步骤已完成、下一步需不需要老板决策。
- **看得见依据**：回答是实际查询、文档引用、模型推断还是资料不足。
- **看得见后果**：执行前写清对象与副作用；执行后提供可重查的结果。
- **看得见恢复**：失败后明确是未执行、已执行但未收到回复，还是无法确定。
- **看得见模拟边界**：使用模拟通道时准确说明模拟范围，不假装真实投递。

### 8.3 视觉与交互

保留 Boss Agent 蓝绿白、大鹏品牌、现有高保真资产与已复用的成熟开源组件，但判断重点改为业务完成效率。老板端减少技术术语和不必要的固定字段；管理员端保留必要配置密度。小窗口与 200% 缩放仍需验收，组件是否“接近设计稿”不能替代连贯的任务体验。

### 8.4 角色与数据

实际角色只有 BOSS 与 MAINTAINER；联系人、处理人属于模拟／业务资料对象，不自行扩展成拥有产品登录权限的第三类角色。真实本机账号、授权、来源有效性、读写范围和幂等必须遵守现有服务端边界。语音继续暂停；没有额外授权不发起新的真实外部调用，不重启或覆盖用户正在使用的实例。

## 9. 建议的迭代顺序、依赖与交付标准

**建议改变“按页面数统计进度”的产品关注重点**：工程仍遵守当前正式任务与受控目录，但产品验收优先从 P0 业务故事入手。下表是推荐的下一阶段设计与验收顺序，不擅自修改 feature-delivery.json 或当前唯一活动任务。

| 阶段 | 关键页面／模块 | 首要交付结果 | 准入和退出条件 |
| --- | --- | --- | --- |
| **I：聊天真正具备 Agent 能力** | N02、A08、A09、A15、D01—D03；nanobot Runtime / Tool Registry | 能通过自然语言查真实业务工具结果、说明来源、显示运行步骤和失败 | 准确候选可启动，CHAT-E2E-01、05 与当前权限安全检查通过 |
| **II：交办闭环** | F01、N02、N05、F06、F08、F29、F28 | 发现事项→确认交办→反馈→催办→验收的同源链路 | US01／US03／US11／US12、幂等与重启通过 |
| **III：经营智能分析** | N03、F02、F03、F14—F23、V19 | BI 服务可复用，指标／专题解释有口径与依据 | US02 与关键专业指标场景通过；缺数据正确表达 |
| **IV：会议和决策秘书** | N04、F04、F05、F07、F09—F12 | 会前材料、纪要确认、审批、研究、行程形成闭环 | US04／US05／US07 正常与异常路径通过 |
| **V：记忆和主动工作** | F13、N06—N11、A06、A07、A13 | 有效目标／记忆在会话采用，授权计划能触发与停止 | US06／US08、权限与失效传播通过 |
| **VI：管理员运营和全量用户验收** | A01—A16、F25、F30—F32、公共页面 | 配置／发布／运行／评测／恢复／交接可独立执行 | US09／US10／US13 及 72 页面／变体最终清单通过 |

**优先复用而非重造**：

1. nanobot AgentLoop、SessionManager、CronService、WebSocket 与 ClientProvider。
2. 现有经营 BI、任务状态机、会议、审批、记忆、来源和调度服务。
3. 现有权限、CAS、授权与幂等回执，不新增第二套业务真相源。
4. 现有 V7 页面与品牌组件，不因为开展 Agent 集成而降低页面信息结构。

建议后续用“完成多少条端到端用户故事、能安全执行多少类工具、恢复是否可靠”替换“又开发了几个静态页面”的汇报中心。仍要单独保留每个页面的验收记录，避免业务故事通过掩盖视觉和局部交互问题。

### 9.1 首个建议完整示范

先做“经营异常分析 → N02 连续追问 → 生成交办草稿 → BOSS 授权 → N05/F06 追踪 → 异常提醒 → BOSS 结果核查”。该路径涵盖 Agent、BI、数据来源、任务状态、权限、通知和恢复，最能证明产品与普通聊天＋后台表单的区别。

### 9.2 第一阶段建议质量门槛（目标值，非实测）

| 指标 | 建议门槛 |

| 五条 N02 P0 验收主线 | 全部完成适用场景 |
| 未授权业务写入／虚构已执行／重复写入 | 0 |
| 业务结果与有效来源可追溯 | 适用场景 100% |
| 工具返回与界面宣称结果一致 | 适用场景 100% |

## 10. 对开发和 QA 的具体接收要求

### 10.1 必需的两套交付视角

- **老板使用报告**：每项用户故事的起点、输入、页面路径、Agent 执行结果、老板确认点、最终业务对象及能解决的实际问题。
- **管理员排查报告**：本次运行采用的模型、Prompt、Skill、Tool、数据集与知识版本；工具轨迹、错误位置、恢复措施和回滚依据。

两个报告可以由同一次真实执行产生，但必须使用同一准确候选。不要通过模型自动生成“已成功”的叙述替代业务系统证据。

### 10.2 建议的缺陷条目字段

| 字段 | 要求 |
| --- | --- |
| defect_id / story_id / page_id | 稳定可追溯，如 US03 / N02 / F06 |
| 严重程度 | P0/P1/P2，解释影响到的真实用户任务 |
| 证据等级 | FACT、CHECK 或 PROPOSAL；未实测只能标 CHECK |
| 复现条件 | 版本、角色、数据、时区、对象、操作序列 |
| 预期与实际 | 尽量填写可观察的状态、ID 和返回，而非泛泛“体验不好” |
| 定位和修复归属 | 页面／工具／领域／配置／公共运行框架及依赖 |
| 验证结果 | 通过、失败、阻塞、未运行；关联准确提交与最小证据 |
| 剩余风险 | 真模型、外部通信、宿主设备、用户验收等未覆盖范围 |

### 10.3 优先排查的 10 个候选问题

1. 聊天能输入但无法触发任何有意义的业务工具。
2. 模型编造经营数值、原因、引用或“已发送”结果。
3. 业务页面独立可用，聊天无对应可选工具。
4. 经营追问无法继承或明确更改当前范围。
5. 交办草稿与任务中心不是同一个对象和版本。
6. 老板不确认也会发生写入，或技术管理员代替老板授权。
7. 运行中断后重复提交造成重复任务／消息。
8. 资料换版／撤销后，旧结论继续标记为当前有效。
9. 页面／会话／角色切换后出现旧异步数据或敏感信息泄露。
10. 构建、运行实例和报告引用的提交不是同一版本。

以上条目是应排查的候选风险，**不是本次实际发现并复现的 10 个 Bug**。

### 10.4 真实启动与逐页验收前置条件

接手者必须先完整阅读 [开发接手与执行规范](开发接手与执行规范.md)，从唯一状态确认活动工单、准确源码、制品与允许目录。受保护的用户服务、账号、凭据及 SQLite 不应被覆盖；新验收使用隔离数据、端口与构建。按照正式工单确定的真实运行入口启动，同时留存版本与环境记录。本文既不授权新增外部 API 请求，也不解除语音／主动截图限制。

需要在实际运行后为每个视图补充 PASS／FAIL／BLOCKED／NOT_RUN 以及准确复现证据；在此之前，不能使用“全部 72 页已验收”的表述。

## 11. 结论与下一步

从 GitHub 现有源码和正式记录看，Boss Agent 已有较丰富的前端、领域服务、Agent 适配及历史限定开发成果，继续复用是合理的。然而，从老板的真实产品感受看，最值得优先投入的是**聊天是否真能驱动经营查询、任务交办、授权、结果恢复和持续跟踪**。如果 N02 不能成为这些业务的入口，即使 72 个视图都能打开，也难以构成一个有差异化价值的老板 Agent。

**推荐的下一项产品验证**：以 US02＋US03＋US11 组成一个“采购成本异常调查和交办”端到端用例，在准确可运行候选中先贯穿 N02、F03、F14、D01、D02、N05、F06、D03、A09、A15。拿到实际结果后，按证据逐项修复，再扩展全部页面。

本文属于产品评估与后续验收方案。它不修改现有开发状态、完成计数、用户验收记录，不替代实际运行的逐页验收，也不自动改变当前实施排队或用户已确认的安全边界。
